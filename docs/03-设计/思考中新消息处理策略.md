# 思考中新消息的处理策略（待决策）

> **状态：方案已讨论，尚未实现。** 记在这里是为了不丢结论，等真正遇到问题时按此实现。
>
> 最后更新：2026-10-22

---

## 一、问题

AI 处理一条消息（LLM 思考 + 工具循环）实测要 **5~15 秒**。这期间如果同一会话又来新消息：

```
消息A → 回复模式判断 → 进会话队列（debounce 合并）→ 开始处理
                                                       ↓
消息B 到达  ──────────────────────────────→ 只能排队等这一轮结束
消息C 到达  ──────────────────────────────→
                                                       ↓
                                                  发消息
```

**当前行为**：B、C 在队列里等着，A 这轮跑完再合并处理 B+C。

**体感问题**：用户会觉得"反应慢"，尤其在对话节奏快的时候。

---

## 二、三个候选方案

### 方案 A：分层（"发首条前可中断"）

```
新消息到达 → 我发过消息了吗？
  ├─ 没有 → 中断当前思考，合并新消息重来
  └─ 发过了 → 排队等这一轮结束
```

| 优点 | 缺点 |
|---|---|
| 实现简单（一个"已发出消息"标志即可） | **消息密集时会反复中断**，可能一直发不出去 |
| 不会打断"半截对话"（用户已看到部分回复） | 判定太粗：群聊闲聊也会触发中断 |

### 方案 B：并行预判断

```
新消息到达 → 立即跑一次轻量 JEV 判断（该不该打断？）
  ├─ 重要（被 @ / 私聊 / 直接问句）→ 中断重来
  └─ 不重要 → 排队
```

| 优点 | 缺点 |
|---|---|
| 判定精准，不会被闲聊打断 | **每次多一次判断调用**（成本 + 200~500ms 延迟） |
| 和 JEV 的判断体系天然一致 | 判断本身也有失败可能（需要降级） |

### 方案 C：组合（推荐）

```
新消息到达 → 我发过消息了吗？
  ├─ 没发 →
  │    ├─ 私聊 → 直接中断（不必判断：私聊就是专门在跟我说话）
  │    └─ 群聊 → 跑一次判断 → 重要才中断
  └─ 发过了 → 排队（保护半截对话）
```

| 优点 | 缺点 |
|---|---|
| 两层保护：没发消息时不会被"半截"困住 | **实现最复杂**（三个分支） |
| 私聊响应最快 | 需要"连续中断上限"防抖 |
| 群聊不会被闲聊打断 | |

## 四、无论选哪个都必须有的：连续中断上限

否则消息刷屏时会**无限中断**，AI 永远跑不完一轮：

```
同一轮最多中断 2 次；超过就强制跑完，新消息排队。
```

理由：中断的收益是"更快的响应"，但代价是"永远不响应" —— 后者显然更坏。

## 五、实现时要注意的点

| 点 | 说明 |
|---|---|
| **CancellationToken 传播** | 已经贯穿 LLM 调用，中断有基础设施可用 |
| **状态回滚** | 中断后已写入的消息/工具副作用**不能回滚**（比如已经发出 1 条），所以方案 A/C 的"是否已发消息"标志必须可靠 |
| **与 debounce 的关系** | 现有 debounce 是"来了就等一会再处理"，本策略是"处理中又来"，两者不冲突但顺序要对 |
| **审计** | 中断是可观察行为，建议记一条 metrics（`reply.interrupted`） |
| **和 JEV 的关系** | 方案 B/C 复用现有 `IReplyModeDecider` 的判断能力，不要另造一套 |
