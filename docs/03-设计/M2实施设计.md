## 2. 阶段拆分

| 阶段 | 内容 | 验收标志 | 依赖 | 规模 |
|---|---|---|---|---|
| **M2-A** | **HTTP `POST /api` + `WS /events` + 鉴权** | `curl` 调通 5 个 action；WS 收到 `hello` / `qq.state`；非 loopback 无 token **拒绝启动** | 无 | M |
| **M2-B** | 配置层：引导/运行分离 + Data Protection 加密 + 配置 API | key 加密落库、掩码回显、改配置不重启生效 | A | L |
| **M2-C** | 命令系统 12 条 | 命令不交模型；权限正确（管理员 / 白名单 / 普通） | A | M |
| **M2-D** | WinUI3 客户端（骨架 → 连接状态 → 聊天列表 → 配置页 → 日志下载） | 能连、能看、能配、能下载 | A + B | XL |
| **M2-E** | 通知响应（5 类）+ `jev` 模式 + 完整可观测 | 各自验收 | A | M |

**推进方式**：一个阶段做完 → 用户抽查 → 下一个阶段。每阶段独立可交付、可验收、随时可停。

> **为什么 A 必须最先**：客户端、配置 UI、命令、日志下载**全部**要经过端点。
> 先立端点，后续每个阶段都能用 `curl` 验证，不必等 UI 起来才知道对不对。

### 3.3 接口定义

**命令**：`POST /api`

```json
// 请求
{ "action": "ping", "payload": null }

// 响应（与 docs/05-契约/command-ping.json 一致）
{ "code": 0, "message": "ok", "data": { "serverTime": 1789999200000, "serverVersion": "0.1.0" } }
```

| code | 含义 |
|---|---|
| `0` | 成功 |
| `400` | payload 参数不合法 |
| `401` | 未提供或 token 错误 |
| `404` | 未知 action |
| `500` | 服务端异常（message 带简短原因，**不带堆栈**） |

**M2-A 的 5 个 action**：

| action | payload | data |
|---|---|---|
| `ping` | — | `{ serverTime, serverVersion }`（毫秒时间戳） |
| `getStatus` | — | `{ uptimeSeconds, channelConnected, model, sessions, pendingTasks }` |
| `listSessions` | `{ limit? }` | `[{ sessionId, chatType, messageCount, lastMessageAt }]` |
| `getMessages` | `{ sessionId, limit? }` | `[{ id, isOutgoing, sender, text, occurredAt }]` |
| `getMetrics` | `{ windowHours? }` | `[{ kind, count, avgMs, minMs, maxMs, totalInputTokens, totalOutputTokens }]` |

**事件**：`WS /events`，帧格式固定（架构 §3.5，**`time` 是 Unix 毫秒**）：

```json
{ "type": "hello", "seq": 1, "time": 1789999200000, "data": { "serverVersion": "0.1.0", "capabilities": ["qq", "agent", "session"] } }
```

| type | 何时发 | data |
|---|---|---|
| `hello` | 连接建立 | `{ serverVersion, capabilities }` |
| `qq.state` | 通道连接状态变化 | `{ connected }` |
| `agent.event` | `AgentEvent`（漂移 / 降级） | `{ kind: "drift" \| "degraded", sessionId, detail }` |

> **`seq` 的口径**：`hello` / 初始 `qq.state` 是**连接级初始帧**，`seq = 0`；
> 之后由广播器发出的业务事件从 **1** 开始全局递增（所有客户端共享同一序号）。

> 消息收发事件（`message.received` / `message.sent`）留到 M2-D 做「聊天列表实时刷新」时再加 —— **先只做能验的三类**。

### 3.4 鉴权

| 场景 | 规则 |
|---|---|
| 监听地址是 **loopback** | 免验（本机单用户部署，FR-16 原定） |
| 非 loopback | **必须**配 `ZIPPER_HTTP_TOKEN`，否则**启动即拒绝**；请求需带 `Authorization: Bearer <token>` |
| token 比较 | 定长比较（`CryptographicOperations.FixedTimeEquals`），避免时序侧信道 |

### 3.5 验收标准

| # | 标准 |
|---|---|
| A1 | `curl -X POST http://127.0.0.1:5180/api -d '{"action":"ping"}'` → `code:0` + `pong:true` |
| A2 | 5 个 action 全部返回结构合法的响应（未知 action → `404`） |
| A3 | WS 连上后第一帧是 `hello`，`seq` 从 1 递增 |
| A4 | 用 `curl` 连 WS（或小脚本）能收到 `qq.state` |
| A5 | 监听 `0.0.0.0` 且无 token → **启动失败并说明原因** |
| A6 | 监听 `0.0.0.0` 且有 token：无 token 请求 → `401` |

### 3.6 测试策略

- 没有测试项目 → 用 `curl` / 临时 WS 脚本做 **L1 实测**，命令与原始输出写进验收记录
- 鉴权负向用例（无 token / 错 token）必须实测，不能只读代码
- 端到端：`start → curl 5 个 action → WS 收 hello → 停服务`，全程日志无 `ERR`

## 4. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Kestrel 与现有 NapCat 长连接共存 | 端口 / 生命周期冲突 | Kestrel 只监听 HTTP，NapCat 仍是出站 WS，互不相干；端点开关做成配置项 |
| 客户端（M2-D）构建风险高 | WinUI3 无模板、需手写 csproj | 客户端最后做；先用 `curl` 把所有能力验完，UI 只做展示 |
| 契约双份（Server/Client 各一套 DTO） | 漂移在编译期发现不了 | `docs/05-契约/` 样例随实现同步；M2-D 时用样例做断言 |
| 配置热更新范围不清 | 改一项影响全局 | M2-B 只承诺「LLM 参数 / 人设 / 上下文参数」热更新，其余仍要重启 |

### 6.2 与计划的差异

| 计划 | 实际 | 原因 |
|---|---|---|
| `getMessages` 带 `beforeId` | **只支持 limit** | 「往前翻页」需要新查询，M2-A 用不到；等 M2-D 做 UI 时再补 |
| 事件 `seq` 从 1 起 | `hello` / 初始 `qq.state` 为 `seq=0` | 初始帧不占全局序号，业务事件仍从 1 递增 |
| 原 `Microsoft.Extensions.Hosting` 包 | **删除** | 框架引用已提供；保留会触发 NU1510 |
