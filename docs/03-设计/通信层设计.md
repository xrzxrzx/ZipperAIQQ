## 1. 目标与约束

### 1.1 要解决什么

**一份 WebSocket 逻辑，服务端与客户端共用。** 这是它能成为独立项目、且位于依赖最底层的唯一理由。

三种连接场景，全靠同一套实现：

| 场景 | 谁发起 | 本项目的角色 |
|---|---|---|
| WinUI3 客户端 → 服务端 | 客户端 | **服务端**（接受连接）+ **客户端**（发起连接） |
| 服务端 → NapCat 正向 WS | 服务端 | **客户端**（发起连接） |
| NapCat 反向 WS → 服务端 | NapCat | **服务端**（接受连接） |

### 1.2 硬约束

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **零业务依赖**：不认识 OneBot、不认识 HTTP 契约 | 否则没法给客户端复用 |
| 2 | **不读任何业务配置** | 旧项目 `InitClient()` 直接读 NapCat 的 IP/端口 → 传输层被业务绑定 |
| 3 | 载荷类型用 `JsonNode`（`System.Text.Json`） | 全项目 JSON 统一 |
| 4 | 不引用 WinUI3 / Windows 专有程序集 | 服务端跨平台（见技术设计 §2.3 约束 1） |
| 5 | 不依赖 `Server` / `Client` / `Agent` / `Channels` | 它位于依赖图最底层 |

## 2. 复用的切口

**服务端和客户端的 WebSocket 是两个 API**：

```csharp
// 服务端
WebSocket socket = await HttpContext.WebSockets.AcceptWebSocketAsync();

// 客户端
var socket = new ClientWebSocket();
await socket.ConnectAsync(uri, ct);
```

**但两者都是 `System.Net.WebSockets.WebSocket` 的子类** ← **这就是复用的地基**。

### 2.1 复用的边界

| 能力 | 复用？ | 说明 |
|---|---|---|
| 帧收发 | ✅ | `SendAsync` / `ReceiveAsync` 是基类方法 |
| 分帧拼装 | ✅ | 循环读到 `EndOfMessage` |
| 消息编解码 | ✅ | `JsonNode` ↔ UTF-8 JSON |
| 心跳 / 保活 | ✅ | 应用层帧（见 §6.2） |
| 背压 / 有界队列 | ✅ | 见 §6.3 |
| 并发发送串行化 | ✅ | 见 §6.4 |
| 关闭握手 | ✅ | 见 §6.5 |
| **建连方式** | ❌ | 服务端"接受" vs 客户端"发起" |
| **重连** | ❌ 仅客户端 | 服务端是被动的，不需要主动重连 |
| **消息分类** | ❌ | 由调用方**注入委托**（见 §4） |

### 2.2 结构

```
                    ┌────────────────────────────────────────┐
                    │  IWebSocketTransport（公开契约）        │
                    └───────────────────┬────────────────────┘
                                        │
                    ┌───────────────────┴────────────────────┐
                    │  WebSocketDuplexBase（abstract）        │
                    │  · 收/发/分帧/心跳/背压/关闭  —— 只写一遍 │
                    │  · protected abstract WebSocket Socket  │
                    └────────┬──────────────────────┬────────┘
                             │                      │
              ┌──────────────┴───────┐   ┌──────────┴─────────────┐
              │ ServerSideTransport  │   │ ClientSideTransport    │
              │ 包一个已接受的 socket  │   │ 负责建连 + 重连         │
              └──────────────────────┘   └────────────────────────┘
```

**关键**：子类**只提供 `Socket`**（以及客户端多一个重连策略），其余全部继承。

## 3. 接口设计

### 3.1 公开契约

```csharp
public interface IWebSocketTransport : IAsyncDisposable
{
    bool IsConnected { get; }

    /// 发送一条 JSON 消息（内部串行化，可并发调用）
    Task SendAsync(JsonNode message, CancellationToken ct);

    /// 接收消息流。⚠️ 只能枚举一次（见 §3.4）
    IAsyncEnumerable<JsonNode> ReceiveAsync(CancellationToken ct);

    /// 连接状态变化（Connecting / Connected / Disconnected）
    event Action<TransportState>? StateChanged;

    Task CloseAsync(WebSocketCloseStatus status, string? reason, CancellationToken ct);
}

public enum TransportState { Disconnected, Connecting, Connected, Closing, Closed }
```

### 3.2 为什么载荷是 `JsonNode` 而不是 `byte[]` / `string`

- 本项目的**所有** WS 对话都是 JSON（OneBot 事件、管理客户端事件帧）→ 统一用 `JsonNode` 让上层免去解析
- **代价**：不支持二进制帧。若将来要传原始二进制（如不经 base64 的图片），需要扩展接口（见 §10 Q1）

### 3.3 分类委托（**关键设计**）

传输层不认识 `post_type`，也不认识 `echo` —— 它们是 OneBot 语义。**怎么分类、怎么取关联 id，由调用方注入**：

```csharp
/// 这条消息是 API 响应还是事件？
public delegate MessageKind ClassifyMessage(JsonNode raw);
public enum MessageKind { Event, ApiResponse }

/// 从消息里取"关联 id"（OneBot 里就是 echo）
public delegate string? ExtractCorrelationId(JsonNode raw);
```

**这两个委托让 `Transport` 真正通用了**：它能服务任何"消息分两类、其中一类有关联 id"的协议。

> **对比旧项目**：`NapCatWebSocket.RawMessageArried` 里直接写 `rawJSON["post_type"]` 判断 —— 那是把 OneBot 语义焊死在传输层里。注入委托是它的正确形态。

### 3.4 ⚠️ `ReceiveAsync` 只能有一个消费者

`IAsyncEnumerable<T>` **不是**多播的 —— 第二次枚举行为未定义（多数实现会抛异常）。

**所以不能这样**：

```csharp
// ❌ 两个模块各订阅一次
_ = Task.Run(async () => { await foreach (var m in t.ReceiveAsync(ct)) eventBus.Publish(...); });
_ = Task.Run(async () => { await foreach (var m in t.ReceiveAsync(ct)) apiRouter.Complete(...); });
```

**正确做法：`Channels.NapCat` 单点消费，读出来自己分流**（见 §4）。

> 这也是**分流逻辑不能放在 `Transport`** 的直接原因。

## 4. 消息分类与分流

### 4.1 分流图

```
WS 收到一帧
   │
   ▼
Transport.ReceiveAsync()            ← 单一消费者
   │
   ▼
Channels.NapCat 的接收循环          ← 分流发生在这里（OneBot 语义）
   │
   ├─ classify(raw) == Event
   │     └─▶ IEventBus.Publish(new QqEvent(...))              ← 1:N 广播
   │
   └─ classify(raw) == ApiResponse
         └─▶ IResponseRouter.TryComplete(extractId(raw), raw)  ← 1:1 定向，O(1)
```

### 4.2 为什么分两条路

| | 天生语义 | 匹配的机制 |
|---|---|---|
| **事件** | **1:N 广播**（一个事件被多个订阅者消费） | 事件总线 ✅ |
| **API 响应** | **1:1 定向**（一个关联 id 恰好一个等待者） | `ConcurrentDictionary<id, TaskCompletionSource>` ✅ |

**若把 API 响应也塞进事件总线**，会撞三件事：

1. 有 N 个 pending 请求时，**每个响应被广播给所有等待者**（O(N) 无谓开销）
2. 事件总线**没有"消费"语义** —— 订阅者无法把事件"取走"，只能各自过滤
3. 每次 API 调用都要**订阅/退订一次**，白付容器增删成本

### 4.3 请求-响应配对与超时

```csharp
// 发出请求时
var echo = Guid.NewGuid().ToString("N");
var tcs = new TaskCompletionSource<JsonNode>(TaskCreationOptions.RunContinuationsAsynchronously);
_pending[echo] = tcs;
try
{
    await transport.SendAsync(BuildRequest(action, payload, echo), ct);

    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
    cts.CancelAfter(timeout);
    return await tcs.Task.WaitAsync(cts.Token);
}
finally
{
    _pending.TryRemove(echo, out _);      // 成功 / 超时 / 取消 都清理，不泄漏
}
```

**要点**：

- 超时绑定在**实例**上，不是绑定"事件类型" → **不需要给事件总线加"某类事件的超时机制"**
- `RunContinuationsAsynchronously`：避免在 `TryComplete` 的线程上同步跑延续（可能造成栈深/阻塞）
- **收到未知关联 id 的响应要告警**（说明有响应没人等 → 可能是超时后迟到的响应，或协议异常）

## 5. 必须处理的坑

| # | 坑 | 现象 | 对策 | 旧项目的教训 |
|---|---|---|---|---|
| 1 | **单帧大小限制** | 大消息（长文本、base64 图片）被截断 | 循环读到 `EndOfMessage`；设 `MaxMessageBytes` 上限 | `buffer = new byte[1024]` 固定 → 真修过一次 |
| 2 | **中间设备静默断连** | NAT/代理丢弃连接，双方都不知道 | **应用层心跳** + 超时判定（别只依赖控制帧 ping/pong） | 心跳只打日志，没做判活 |
| 3 | **并发发送帧交错** | 多任务同时 `SendAsync` → 帧错乱 | `SemaphoreSlim(1,1)` 串行化发送 | 未处理 |
| 4 | **消费慢 → 内存爆** | 接收队列无限增长 | **有界队列 + 背压**（满则暂停读取） | 用 `ThreadPool.QueueUserWorkItem` 无上限 |
| 5 | **未处理关闭帧** | 连接关不干净、资源泄漏 | 收到 `Close` → 回发 → 完整关闭流程 | `Disconnect()` 判断反了，且从不 `CloseAsync` |
| 6 | **断线不重连** | 客户端要手动重启 | 客户端侧指数退避 + 抖动 | 完全没有重连 |

### 5.1 ⚠️ 反面教材：`catch` 后直接 `continue`

旧项目 `NapCatWebSocket.Recveive` 的写法：

```csharp
// ❌ 连接断开后，catch 捕获异常 → while 继续 → 立刻再抛 → 死循环刷日志
while (!token.IsCancellationRequested)
{
    try { ... ReceiveAsync ... }
    catch (Exception ex) { logger.Error("接收消息失败: " + ex.Message); }
}
```

**正确写法**（见编码规范 §3.4）：区分异常类型 + 指数退避 + 取消支持 + **致命错误要跳出循环**。

## 6. 实现要点

### 6.1 分帧与拼装

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(_bufferSize);
try
{
    using var ms = new MemoryStream();
    WebSocketReceiveResult result;
    do
    {
        result = await socket.ReceiveAsync(buffer.AsMemory(), ct);

        if (result.MessageType == WebSocketMessageType.Close)
        {
            await HandleCloseAsync(ct);
            yield break;                                   // 结束接收
        }

        ms.Write(buffer, 0, result.Count);
        if (ms.Length > _maxMessageBytes)
            throw new TransportException($"消息超过上限 {_maxMessageBytes} 字节");   // 明确失败，不静默截断
    }
    while (!result.EndOfMessage);

    yield return ParseJson(ms);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);                 // 归还池，别每次 new
}
```

**要点**：
- `ArrayPool` 复用缓冲，避免每次分配（接收是高频路径）
- **超限要抛明确异常**，不要截断（截断会产生"看起来正常但内容缺失"的诡异 bug）
- 用 `yield return` 让 `ReceiveAsync` 天然成为流

### 6.2 心跳

```
发送方：每 HeartbeatInterval 秒发一帧 {"type":"__ping","time":<ts>}
        （不经过上层，由 Transport 内部处理）
接收方：收到 __ping → 回 {"type":"__pong","time":<原 ts>}
判活：  记录"最后一次收到任何帧"的时间
        超过 HeartbeatTimeout 秒没收到任何帧 → 判定断开
```

**两个关键点**：

1. **判活基于"收到任何帧"，不是只基于 pong** —— 否则有正常数据流时也会误判超时
2. **心跳帧要能穿透上层** —— 建议用内部保留前缀（如 `__ping`）并在 `ReceiveAsync` 里**过滤掉**，不让业务看到

**参数建议**：间隔 30s，超时 90s（3 倍容错）。

### 6.3 背压

```csharp
// 有界队列：满了就 await 等待（自然背压）
var channel = Channel.CreateBounded<JsonNode>(new BoundedChannelOptions(capacity)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
});
```

**为什么选 `Wait`（暂停读取）而不是丢弃**：

- 对 NapCat 事件，**消息丢了就是丢了**（不可恢复）
- 暂停读取 → TCP 接收窗口填满 → 对端自然减速 —— 这是**正确的背压**
- **代价**：业务处理太慢时，NapCat 可能超时断开连接 → 但这比"静默丢消息"好得多（至少能发现）

**若将来有"可丢弃"的流量**（如日志推送），可以给它单独的低优先级队列。

### 6.4 并发发送串行化

```csharp
private readonly SemaphoreSlim _sendLock = new(1, 1);

public async Task SendAsync(JsonNode message, CancellationToken ct)
{
    var bytes = Encode(message);
    await _sendLock.WaitAsync(ct);
    try     { await socket.SendAsync(bytes, WebSocketMessageType.Text, true, ct); }
    finally { _sendLock.Release(); }
}
```

**WebSocket 的 `SendAsync` 不保证并发安全** —— 两个线程同时发会让**帧交错**，对端解析全乱。必须串行化。

### 6.5 关闭握手

```
1. 调用方请求关闭（或收到对端 Close 帧）
2. StateChanged → Closing
3. 停止接收循环（取消 CTS）
4. 发送 Close 帧：socket.CloseOutputAsync(NormalClosure, reason, ct)
5. 等待对端关闭（带超时，如 5s）
6. 强制 Dispose socket
7. StateChanged → Closed
```

**要点**：`CloseAsync` 必须**幂等**（重复调用不报错），且**超时后强制释放**（不能因为对端不回应就永远挂着）。

### 6.6 重连（**仅客户端**）

```csharp
// 指数退避 + 抖动
var delay = Math.Min(initialDelay * Math.Pow(2, attempt), maxDelay);
var jitter = delay * jitterRatio * Random.Shared.NextDouble();
await Task.Delay(delay + jitter, ct);
```

| 要素 | 说明 |
|---|---|
| **指数退避** | 1s → 2s → 4s → ... 封顶 60s |
| **抖动** | 避免多客户端同时重连造成"惊群" |
| **状态上报** | 重连期间 `StateChanged` 要发 `Connecting` |
| **重连成功后** | 必须**重新启动接收循环**（旧循环已随 socket 失效） |
| **上限** | 可选：无限重连（长跑服务）或设次数上限（一次性工具） |

**服务端适配器不需要重连** —— 它手里的 socket 来自一次 HTTP 升级，断了就是断了，由对端重新连。

## 7. 配置模型

```jsonc
"Transport": {
  "BufferSize": 16384,                    // 每次 ReceiveAsync 的块大小
  "MaxMessageBytes": 8388608,             // 单条消息上限（8 MB），超限明确失败
  "ReceiveQueueCapacity": 1000,           // 有界队列容量
  "SendTimeoutSeconds": 30,
  "HeartbeatIntervalSeconds": 30,
  "HeartbeatTimeoutSeconds": 90,
  "CloseHandshakeTimeoutSeconds": 5,

  "Reconnect": {                          // 仅客户端使用
    "Enabled": true,
    "InitialDelayMs": 1000,
    "MaxDelayMs": 60000,
    "JitterRatio": 0.2
  }
}
```

> `Transport` **不自己读配置** —— 由调用方（`Server` / `Client`）读好后以 options 对象注入（遵守 §1.2 约束 2）。

## 8. 测试策略

**怎么造 WebSocket 对**：

- 单元测试：用 `WebSocket.CreateFromStream()` 造一对内存管道，或用自建 `FakeWebSocket`
- 服务端集成：`Microsoft.AspNetCore.TestHost` 的 `TestServer`

| 测什么 | 断言什么 |
|---|---|
| **分帧拼装** | 把一条大消息切成多段喂入 → 拼出完整 `JsonNode` |
| **超限保护** | 超过 `MaxMessageBytes` → 抛异常（**不是静默截断**） |
| **并发发送** | 多线程并发 `SendAsync` → 所有帧完整、无交错 |
| **心跳超时** | 模拟对端静默 → 超时后状态变 `Disconnected` |
| **心跳不误判** | 持续有数据流但无 pong → **不应**判超时 |
| **关闭握手** | 对端发 Close → 我方回发 Close 且资源释放、`CloseAsync` 幂等 |
| **背压** | 消费者故意慢 → 队列不无限增长（`Wait` 模式生效） |
| **重连** | 断开 → 按退避重连；抖动在配置范围内 |
| **`JsonNode` 往返** | 中文 / emoji / 大整数 / 深层嵌套 → 序列化往返一致 |
| **异常不吞** | 接收循环里的致命异常 → **上抛**，不是死循环 |

> ⚠️ **`JsonNode` 往返测试要注意**：`System.Text.Json` **默认区分大小写**，字段名写错会**直接反序列化失败**（这比 Newtonsoft 的宽松匹配更安全，但也意味着测试里不该出现"靠宽松匹配侥幸通过"的用例）——见 [`docs/05-契约/README.md`](../05-契约/README.md)（**公开面**）。

## 9. 分期与验收标准（P1）

| 项 | 验收标准 |
|---|---|
| 双端适配器 | 客户端与服务端两个实现能**互发互收** |
| 大消息 | > 100 KB 的消息**完整传输**，不被截断 |
| 超限保护 | 超 `MaxMessageBytes` → **明确抛异常** |
| 并发发送 | 多线程并发发送**不交错** |
| 心跳 | 对端静默 → 能在 `HeartbeatTimeout` 内判定断开；有数据流时不误判 |
| 关闭 | 关闭握手完整、无资源泄漏、`CloseAsync` 幂等 |
| 重连 | 客户端断线自动重连（退避 + 抖动） |
| 测试 | 上述全部有对应单测 |

**P1 不需要**：二进制载荷、压缩（per-message deflate）、多路复用。
