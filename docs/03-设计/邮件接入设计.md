## 2. 总体设计

### 2.1 位置：进程内模块（决策一）

```
MailSource : IMessageSource（进程内，IMAP；**由管道负责启停**，见下）
   │  每账号一个 MailAccountSession：连接 → 增量拉取 → **落库**（Append 成功才推水位、才发事件）
   │ ReceiveAsync（事件流**只当唤醒信号**）
   ▼
MailPipeline : BackgroundService（Server 编排层）
   ├─ 待办来源：IMailRepository.GetPendingSummaryAsync / GetPendingDigestAsync（**数据库即队列**）
   ├─ 摘要 → MailSummaryService ──▶ IChatClientProvider
   ├─ 汇总 → MailDigestService（immediate / interval / daily）
   └─ 转发 → IMessageChannel → 主人的 QQ 私聊
```

**不实现 `IMessageChannel`**：邮件只收不发，`SendAsync` 无意义；避免污染接缝 B。

**不实现 `IHostedService`**（§11 M12）：与既有通道完全同构 —— `NapCatChannel` 也不是 `IHostedService`，
而是由消费方 `MessageRouter` 在 `ExecuteAsync` 里调 `_channel.StartAsync(ct)`（`MessageRouter.cs:74`）。
`MailSource` 因此只暴露 `StartAsync` / `StopAsync` / `ReceiveAsync` / `ReloadAsync`，由 `MailPipeline` 负责启停。
好处：Mail 项目不必引 `Microsoft.Extensions.Hosting`（与 Channel 项目保持一致），生命周期只有一处。

**为什么不经 `MessageRouter`**（相对原稿的修正，见 §11 M2）：`MessageRouter` 的职责是「对话消息 → 落库 → 命令 → 决定要不要回」，而邮件是**通知流**，
进对话链路会被迫写一段「进来后立刻委派出去」的分支，还会让邮件的解析错误有机会影响对话接收循环。

**为什么「数据库即队列」**（见 §11 M9）：纯事件驱动一旦丢一个事件，那封邮件就永远停在「没摘要」，而且没人知道；
从库里查待办则天然可重放 —— 重启、当天失败、汇总没转出去，下一轮都能补上。
这与既有 `SchedulePoller` 的取舍一致（FR-14 / D21：不另建内存队列，避免"DB 与内存两份真相"）。

### 2.2 分层与依赖

|---|---|---|
| `ZipperAIQQ.Channel` | 无 | ➕ `IMessageSource`、`IncomingMail` |

> ⚠️ `ZipperAIQQ.Mail` **不依赖 Agent**（通道层不得反向依赖 agent 层）：摘要服务放在 Server，用 `IChatClientProvider` 实现。
>

> `MailSource` 要读账号、`MailAccountSession` 要落库。方向 `Mail → Storage → Channel → Core`，无环，Storage 不回引 Mail。

### 2.3 输出路径：转发给 QQ 主人（决策九）

邮件**不进入对话回复链路**，而是走「摘要 → 汇总 → 转发」：

| 步骤 | 说明 |
|---|---|
| 1. 摘要 | 单封邮件 → ≤3 句中文要点 +「是否需要处理」 |
| 2. 汇总 | 可配：`immediate`（单封即转）/ `interval`（每 N 分钟合并）/ `daily`（每日汇总） |
| 3. 转发 | 通过 `IMessageChannel.SendAsync` 发到**主人私聊**（`ChatRef { Platform="qq", Type=Private, Id=ownerId }`） |
| 4. 失败处理 | 重试 3 次 → 仍失败记 `failed`，客户端可见原因；**不静默丢** |
| 4b. **谁来说**（2026-10-28 用户要求） | 汇总**先交主人私聊的人格 agent**（`IChatAgentPool`）用自己语气转告；agent 没发出去（0 条/异常）→ **回落直发**后再标记转出 |

- 主人未配置 → 邮件照常落库 + 摘要，但**不转发**，客户端显示「未配置主人」
- 转发内容 = 摘要 + 发件人 + 主题（**不发正文全文**，避免刷屏与泄露）
- 第一期只转 QQ；将来可扩展按平台转发

**状态位是"不静默丢"的落点**（见 §11 M6 / M9）：

| 状态 | 存在哪 | 谁推进 |
|---|---|---|
| 邮件已收 | `Mails` 行 | `MailAccountSession`（落库成功后才推 UID 水位） |
| 摘要待做 | `Mails` 有行、`MailSummaries` 无行 | `MailPipeline` 查 `GetPendingSummaryAsync` |
| 摘要成功 / 失败 | `MailSummaries.Status = ok / failed`（失败行**保留**） | `MailPipeline` |
| 汇总待转 | `MailSummaries.Status='ok' AND ForwardedAtMs IS NULL` | `MailPipeline` → `MailDigestService` |
| 已转 | `MailSummaries.ForwardedAtMs` | 转发成功后由 `MailDigestService` 标记 |

> 计时逻辑（immediate / interval / daily 何时该转）放在 `MailPipeline`，`MailDigestService` 只负责
> 「把当前待转的全部转出去」—— 这样 digest 可以脱离时钟做单测（§11 M11）。

## 3. 接口定义

### 3.1 `IMessageSource`（新增，`ZipperAIQQ.Channel`）

```csharp
/// <summary>平台无关的「信息源」：只有入站，没有出站。</summary>
/// <remarks>
/// 与 IMessageChannel 的区别：邮件这类源**只收不发**，
/// 硬套 IMessageChannel 会得到一个永远抛异常的 SendAsync。
/// </remarks>
public interface IMessageSource
{
    /// <summary>平台标识，如 "mail"。与 ChatRef.Platform 对应。</summary>
    string Platform { get; }

    /// <summary>持续接收入站事件；实现方负责断线与重连。</summary>
    IAsyncEnumerable<InboundEvent> ReceiveAsync(CancellationToken ct);
}
```

### 3.2 `IncomingMail`（新增模型）

```csharp
public sealed record IncomingMail : InboundEvent
{
    /// <summary>收信账号 ID（MailAccounts.Id）。</summary>
    public required string AccountId { get; init; }

    public required string Subject { get; init; }
    public required string FromAddress { get; init; }
    public string? FromName { get; init; }

    /// <summary>纯文本正文（HTML 由实现层转文本，截断到配置上限）。</summary>
    public required string BodyText { get; init; }

    public bool HasAttachments { get; init; }
}
```

- `EventId` = RFC `Message-Id`（去重键）
- `OccurredAt` = 邮件 `Date` 头（取平台时间，不取 `UtcNow`）
- `Chat` 字段：填 `ChatRef { Platform = "mail", Type = ChatType.Private, Id = $"{AccountId}/{messageId}" }` 仅用于统一事件形状；**不参与对话路由**

### 3.3 `MailSource` / `MailAccountSession` / `IImapSession`（`ZipperAIQQ.Mail`）

```csharp
public sealed class MailSource : IMessageSource
{
    public MailSource(
        IImapSessionFactory sessions,      // 可替换，单测用假实现
        IMailRepository repository,        // 读账号 + 落库 + 写同步状态
        ICredentialProtector protector,    // 解密授权码（明文只在内存里活一次）
        MailSourceOptions options,         // InitialDays / PollIntervalSeconds / MaxBodyChars
        ILogger logger);

    public string Platform => "mail";

    /// <summary>建立各账号连接并开始拉取（由 MailPipeline 调用，与 MessageRouter 启动通道同构）。</summary>
    public Task StartAsync(CancellationToken ct = default);

    /// <summary>停止拉取并断开所有连接。</summary>
    public Task StopAsync(CancellationToken ct = default);

    public IAsyncEnumerable<InboundEvent> ReceiveAsync(CancellationToken ct);

    /// <summary>账号增删改后热重建（不重启服务）。</summary>
    public Task ReloadAsync(CancellationToken ct = default);
}
```

职责：

- 启动时从 `IMailRepository` 加载**启用**的账号；一个账号一个 `MailAccountSession`
- **单账号失败不影响其他账号**：异常隔离到会话级（各自独立连接、独立指数退避 1s → 60s 封顶）
- 认证失败**不重试**：写 `LastError`（可读、**不含凭据**）后停该账号，等用户修正
- **落库在这一层完成**（§11 M8）：`AppendAsync` 返回新主键（`null` = 已存在）才推 UID 水位、才向管道发事件
  —— 这样"重启 / 重连不重复收信"和"不丢信"由同一条顺序保证，而不是靠事件重放
- `ReceiveAsync` 的事件流**只用于唤醒** `MailPipeline`（待办从库里查，见 §2.1）

### 3.4 `IMailRepository`（`ZipperAIQQ.Storage`）

```csharp
public interface IMailRepository
{
    /// <summary>新增返回新行主键；已存在（同账号同 Message-Id）返回 null，不抛。</summary>
    Task<long?> AppendAsync(IncomingMail mail, CancellationToken ct = default);

    Task<bool> ExistsAsync(string accountId, string messageId, CancellationToken ct = default);
    Task<IReadOnlyList<StoredMail>> ListAsync(string? accountId, int limit, CancellationToken ct = default);
    Task<StoredMail?> GetAsync(long id, CancellationToken ct = default);

    // ── 摘要 / 汇总的状态位（§11 M4：原稿缺这两条驱动链）──
    Task<IReadOnlyList<StoredMail>> GetPendingSummaryAsync(int limit, CancellationToken ct = default);
    Task SaveSummaryAsync(long mailId, string summary, bool needsAction,
        string status, string? error, CancellationToken ct = default);
    Task<IReadOnlyList<StoredMail>> GetPendingDigestAsync(int limit, CancellationToken ct = default);
    Task MarkForwardedAsync(IReadOnlyList<long> mailIds,
        DateTimeOffset? forwardedAt = null, CancellationToken ct = default);

    Task<IReadOnlyList<MailAccount>> LoadAccountsAsync(CancellationToken ct = default);
    Task UpsertAccountAsync(MailAccount account, CancellationToken ct = default);
    Task DeleteAccountAsync(string id, CancellationToken ct = default);

    /// <summary>只更新同步水位与状态（高频写，避免整行覆盖冲掉用户刚改的配置）。</summary>

```

`StoredMail` 是读模型（邮件 + 可选摘要行）：

### 3.5 `IMailSummaryService`（`ZipperAIQQ.Server`）

```csharp
public interface IMailSummaryService
{
    Task<MailSummary> SummarizeAsync(IncomingMail mail, CancellationToken ct = default);
}

public sealed record MailSummary(string Text, bool NeedsAction, string? Error);
```

- 用 `IChatClientProvider` 拿客户端
- **独立 prompt**，不进入任何对话上下文
- 失败重试 3 次（指数退避），仍失败 → `NeedsAction = false` + `Error` 记录，**邮件保留**

### 3.6 `ICredentialProtector`（`ZipperAIQQ.Mail` 内定义）

```csharp
public interface ICredentialProtector
{
    string Protect(string plaintext);
    string? Unprotect(string? cipher);
}
```

> 为什么不在 Mail 里直接依赖 `ISecretProtector`：后者在 `ZipperAIQQ.Server`，Mail 依赖 Server 会倒置。由 Server 注册一个适配器即可。

### 3.7 `MailPipeline`（`ZipperAIQQ.Server`）

```csharp
public sealed class MailPipeline : BackgroundService
{
    public MailPipeline(
        MailSource source,                 // 只为拿"有新邮件"的唤醒信号
        IMailRepository repository,        // 待办来源（数据库即队列）
        IMailSummaryService summaries,
        MailDigestService digest,
        MailOptions options,
        ILogger logger);
}
```

职责与边界：

| 做什么 | 不做什么 |
|---|---|
| 巡检 `GetPendingSummaryAsync` → 调摘要 → 写 `MailSummaries` | **不落库邮件**（源侧已完成） |
| 按 `DigestMode` 判断该不该转 → 调 `MailDigestService.FlushAsync` | **不自己组文本 / 不自己发消息**（那是 digest 的职责） |
| 单轮失败只记日志，下一轮重来 | 不因一封邮件的异常停掉整条管道 |

- 无新邮件时**每 30 秒**巡检一轮（兜底补做上次没做完的摘要 / 没转出去的汇总）
- 有事件时立即唤醒，保证「到达 → 摘要 → 转发」在秒级完成（验收标准 ≤5 分钟）
- 每轮每类最多处理 10 封（避免一次醒来把几十封全打给 LLM）

## 5. IMAP 与三家差异

### 5.1 三家配置

| 邮箱 | IMAP 主机 | 认证方式 | 注意点 |
|---|---|---|---|
| **QQ** | `imap.qq.com:993` | 授权码（非登录密码） | 网页端开启 IMAP 服务 |
| **163** | `imap.163.com:993` | 授权码 | **必须发送 IMAP `ID` 命令**，否则服务端报 `Unsafe Login` |
| **Outlook** | `outlook.office365.com:993` | 应用密码 / OAuth2（**待实测**） | 微软在逐步禁用 basic auth，需先验证应用密码是否仍可用 |

> ⚠️ Outlook 的认证方式是**本方案唯一未验证假设**。S3 第一步就是实测：应用密码可用 → 走简单方案；不可用 → OAuth2（设备码或交互式），工作量 +1~2 天。

### 5.2 同步策略

| 项 | 策略 |
|---|---|
| 首次同步 | 只拉最近 **7 天**（可配 `initialDays`），避免拉全量 |
| 增量 | 按 UID 水位（每账号记 `LastUid` / `LastSyncAtMs`） |
| **落库与水位顺序** | **先 `AppendAsync` 成功，再推水位**（§11 M8）：反过来会在崩溃窗口里丢信。重复投递（重启 / 重连）由唯一索引 + 预检挡住，`AppendAsync` 返回 `null` 时**不推水位也不发事件** |
| 实时 | 支持 IDLE 就用 IDLE；否则轮询（默认 60s，可配） |
| 去重 | RFC `Message-Id` + 唯一索引（`MessageId` 为空时不去重：宁可重复也不误判成同一封） |
| 正文 | HTML 转纯文本（MailKit 的 `TextBody`/`HtmlBody`），截断到 `maxBodyChars`（默认 20000） |
| 单轮上限 | 每轮每账号最多 200 封，剩下的下一轮继续（避免一次醒来把大箱打满） |

### 5.3 连接管理

- 每账号一个 `ImapClient`，**串行操作**（MailKit 的 client 不保证线程安全）
- 断线 → 指数退避重连（1s → 60s 封顶）
- 账号失效（认证失败）→ **不重试**，标记 `LastError`，等待用户修正
- 优雅关闭：`IHostApplicationLifetime` 里断开所有连接

## 6. 摘要链路

### 6.1 输入

- 主题 + 发件人 + 正文（截断）
- **不传附件、不传 HTML 原文**

### 6.2 Prompt 约束

- 输出 JSON：`{ "summary": "≤3 句中文要点", "needsAction": true|false }`
- 明确要求：不编造、信息不足就说不足
- 判断依据：截止日期 / 发票 / 合同 / 需要回复 / 安全问题

### 6.3 失败与重试

| 情况 | 处理 |
|---|---|
| LLM 429/5xx | 指数退避重试 3 次 |
| LLM 4xx（参数错） | 不重试，标记 failed |
| JSON 解析失败 | 重试 1 次，仍失败标记 failed |
| 全部失败 | 邮件**保留**、摘要状态 `failed`、记录原因 |

### 6.4 并发

- `SemaphoreSlim` 限制并发摘要数（默认 2），避免打爆 DeepSeek 配额

## 8. 验收标准

| # | 标准 | 判定方式 |
|---|---|---|
| 1 | 三家各接 1 个账号，能收到新邮件 | 手工发测试邮件，列表可见 |
| 2 | 邮件到达 → 列表可见 **≤5 分钟** | 计时 |

| 6 | 凭据不出现在日志/界面/导出 | 用授权码全文搜索日志与 DB |

| 10 | 主人未配置时不静默丢，客户端可见提示 | 清空主人配置测试 |

## 11. 实施回写（2026-10-27 · S3 开工时对本文的修正）

S3 开工后发现的**设计缺口与修正**，逐条登记在此（分批与进度记在本地文档 `docs/待办/多平台接入-实施进度.md` §6，**不入库**）：

| # | 原稿 | 实际 | 理由 |
|---|---|---|---|
| **M2** | 邮件事件进 `MessageRouter`（§2.1 / §7.2 / §8 注） | 新增 `MailPipeline` 独立消费，`MessageRouter` **零改动** | 邮件是通知流，不进对话链路；塞进 router 会多一个立刻委派出去的分支，还让邮件解析错误有机会影响对话接收循环 |
| **M3** | `ZipperAIQQ.Mail` 只依赖 Channel（§2.2） | 额外依赖 `Storage` | `MailSource` 读账号、会话落库都要它；方向 Mail → Storage → Channel → Core，无环 |
| **M4** | `IMailRepository` 只有 7 个方法（§3.4） | 补 `GetPendingSummaryAsync` / `SaveSummaryAsync` / `GetPendingDigestAsync` / `MarkForwardedAsync` | 没有这 4 个，「摘要待做」和「汇总待转」两条状态链无从驱动；纯新增，不改既有签名 |
| **M5** | `MailAccounts` 无 UID 列（§4.1） | 增 `LastUid` | §5.2 要求按 UID 增量，表结构漏了该列则每次只能重扫 |
| **M6** | `MailSummaries` 无转发状态（§4.3） | 增 `ForwardedAtMs` + 索引 | 没有它 interval / daily 模式每次都会把同一批邮件再转一遍 |
| **M8** | 落库在消费侧（§2.1） | 落库在 `MailAccountSession`（源侧），`AppendAsync` 成功才推水位、才发事件 | 保证「不丢信」与「不重复收信」由同一条顺序保证，而不是靠事件重放 |
| **M9** | 事件驱动 | **数据库即队列**：事件只作唤醒，待办从库查 | 与 `SchedulePoller`（FR-14 / D21）同一取舍；丢一个事件不会让邮件永远停在「没摘要」 |
| **M10** | `AppendAsync` 返回 `bool`（§3.4） | 返回 `long?`（新主键 / `null`=已存在） | 下游摘要要按 `MailId` 写状态；`MessageId` 为空时 `bool` 无法定位行 |
| **M11** | `MailDigestService` 负责「节奏 + 发送」（§2.3） | 节奏在 `MailPipeline`，digest 只做「把待转的全部转出去」 | 计时与发送揉一起，单测要跟时钟打架 |
| **M12** | `MailSource : IMessageSource, IHostedService`（§2.1 / §3.3） | `MailSource` **不实现 `IHostedService`**：由 `MailPipeline` 调 `StartAsync` / `StopAsync` | 与既有通道同构（`NapCatChannel` 也不是 `IHostedService`，由 `MessageRouter.cs:74` 启停）；Mail 项目因此不必引 Hosting 包，生命周期只有一处 |
