### 已决事项（原为待确认风险）

| 项 | 结论 | 理由 |
|---|---|---|
| **节流位置** | 仍包在**最外层**（`Throttled(Composite(...))`） | 节流是"同一账号的发送节奏"，与"发到哪个平台"无关；放内层会变成每平台各算一套，等于没限速 |
| **`Platform` 语义** | 复合通道的 `Platform` = **第一个子通道**（今天 = qq），仅供单值消费者兼容 | 多平台下"一个平台"这个概念本身不成立；新代码一律用 `Platforms` / `SelfIdFor` / 按 `ChatRef.Platform` 路由 |
| **`IContactDirectory`** | 复合通道实现它，**转发主平台** | `ChatAgent.cs:573` 靠 `_channel is IContactDirectory` 决定要不要给模型联系人工具；不实现会导致工具在调用时才炸。按平台查询属 S3-C（决策四） |
| **`SelfIdChanged` 的平台归属** | 现阶段所有子通道的事件都往外抛（不带平台信息） | 事件签名是 `Action<string>`，改签名会动公开契约；**S3-E 落地抖音前必须把持久化键改成按平台**（现在是单键 `bot.selfId`，会被后登录的平台覆盖） |

### 已决事项（原为待确认风险）

| 项 | 结论 | 理由 |
|---|---|---|
| **键形态** | 新前缀 `access.{platform}.*`，旧键**只读不删** | 旧键没有平台语义（`owner.userId`），拼后缀会造出歧义键；只读回退＝老配置零迁移 |
| **写旧键吗** | 写 `qq` 时**同时写一份**旧键 | 万一回退到旧版程序，主人 / 管理员不会突然"消失"；代价是一次多余写 |
| `IRoleResolver` 是否保留单参重载 | **不保留** | 保留会变成"忘了传平台就默认 qq"的静默陷阱；让编译器把 4 个调用点全逼出来改 |
| **工具白名单** 是否平台化 | **不**（保持全局） | 决策四只要求主人 / 管理员 / 黑白名单平台化；工具白名单是"这台机器允许谁动文件"的运维口径，与平台无关 |
| **未配置平台**的过滤行为 | **全放行** | 新平台刚接入不该被另一个平台的名单挡住；显式配置才生效 |
| **启动时是否灌库** | **灌**（C9） | 实测发现原来**只**在 setAccess 时更新内存过滤器，重启后名单回落到环境变量——即"配了也白配"。本次一并修掉 |

| 未登记工具默认 | `All`（通用） | 宁可多给一个"其实没有平台限制"的工具，也不要让新工具默默消失 |
| **`All` 的语义** | 「**不限定平台**」，**含未登记平台** | 踩了位运算坑：`All & None == 0` 会把通用工具全灭，连 `send_message` 都没了（详见台账踩坑） |
| 通知是否拆枚举 | **不拆**，加 `NoticeCatalog` 映射 | 枚举值参与持久化（`Notices.NoticeType` 存 INTEGER）与旧键，拆会动数据兼容 |
| 通知键形态 | `notice.reply:{platform}:{type}`；qq 镜像旧键 | 与 S3-C 的 access 键同口径（新键优先、旧键只读回退、qq 镜像写） |
| `/notice` 命令 | **必须**改走平台键 | 平台化之后它是唯一还在写旧键的路径 → 会出现「命令说开了、行为页显示关」的读写分歧 |
| 客户端保存形态 | `notices` 数组 + 单项 `platform` | `getBehavior` 一次返回全部平台，一次提交跨平台；旧服务端不认该字段 → 客户端检测到无 `platforms` 时**回退老 payload**，避免"假保存成功" |

> ⚠️ **留给 S3-E 的前置**：`NoticeResponder.IsEnabledAsync` 仍只读旧键（qq）。抖音通知类型入表时，
> 它**必须**改成按 `IncomingNotice.Chat.Platform` 读平台键，否则抖音的通知开关"写了但不生效"。
