> **进度唯一真源**：本地文档 `docs/待办/多平台接入-实施进度.md`（**本地，不入库**）
> 原则：**阶段即提交**；每阶段可独立验收；不破坏接缝 A/B/C；单测不打真实外部服务

## 0. 总览与顺序

```
S3-A 多通道骨架 ──▶ S3-B 邮件 ──▶ S3-F 配置页
      │                │              ▲
      ├──▶ S3-C 配置平台化 ──▶ S3-E 抖音 ──┘
      ├──▶ S3-D 工具/通知/help
      └──▶ S3-G 消息查询（可与 D 并行）
```

| 阶段 | 内容 | 依赖 | 可独立验收 |
|---|---|---|---|
| **A** | 多通道骨架（`IMessageSource` / `CompositeMessageChannel`） | 无 | ✅ 回归 + 双假通道 |
| **B** | 邮件收信 + 摘要 + 转发 | A（或最小接线） | ✅ 三家收信 |
| **C** | 配置平台化（人员 / 名单 / 角色解析） | A | ✅ QQ/抖音互不影响 |
| **D** | 工具适配 + 通知口径 + help 图片 | A | ✅ 工具过滤 |
| **E** | 抖音 sidecar + `/ws/channel` | A、C | ✅ 真机收发 |
| **F** | 第三方平台配置页 | B、E | ✅ 两 Tab 可配 |
| **G** | 消息查询跨平台增强 | 无 | ✅ 结果带平台 |

> **执行顺序已定（2026-10-27 用户）**：**S3-B 邮件先做** → A/C → D/G → E → F。
> 理由：B 只需要 `IMessageSource` + 自己的管道，**不依赖 A**（A 的 `CompositeMessageChannel` 是为"多通道出站路由"服务的，
> 邮件不需要）；B 独立且能最快看到真实价值。A 的 `IMessageSource` 已在 B-1 里落地，A 剩下的工作不再阻塞 B。

### 目标

- 引入 `IMessageSource`（只有入站的源）
- `CompositeMessageChannel` 合并多来源；出站按 `Platform` 路由
- 只注册 NapCat 时**行为与现在完全一致**

### 验收

- 仅 NapCat 时：现有全量测试绿（**回归是硬门槛**）
- 两个假通道同时注册：事件都能进 `MessageRouter`，出站不串平台
- `Platform` 未知的出站消息 → 明确报错，不静默丢

### 风险

- `MessageRouter` 的会话缓冲 / 命令 / 通知路径都要走通，别只测消息
- `ThrottledMessageChannel` 是单通道装饰器；复合后节流语义要确认（建议：仍包在最外层，全局共享）

## 风险与回滚

| 风险 | 阶段 | 缓解 |
|---|---|---|
| MessageRouter 改造引入回归 | A | 先跑全量测试；单通道行为逐项对照 |
| Outlook 认证不可用 | B | 第一步实测；失败转 OAuth2 |
| 名单迁移丢配置 | C | 惰性迁移 + 保留旧键读取 |
| 工具过滤漏标 | D | 默认「通用」，专项工具显式声明 |
| douyin-im 不稳 | E | 小号 POC；sidecar 可独立启停 |
| 配置页结构差异大 | F | 数据块模板抽象，两平台各一个 VM |

**回滚**：每阶段独立提交，出问题按提交粒度回退；不跨阶段混提交。
