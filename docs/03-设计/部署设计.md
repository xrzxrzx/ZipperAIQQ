# 部署设计（Deployment）

> **状态**：草案 · 2026-09-22
> **背景**：用户购入一台**自有服务器（T30，8GB 内存）**，计划把**服务端 + NapCat 跑在它上面**。
> **已有结论**：那台阿里云服务器**各管各的**（本项目不再使用）。

---

## 1. 这条决策为什么"架构上零成本"

部署形态切换**不需要改一行代码** —— 因为架构里有一条**接缝 A**：

> **表现层 ↔ 编排层：必须走 HTTP / WS，不得进程内直连。**
> 理由是「让**本机单体**与**服务器分离**共用同一套代码」。（见 [`../架构方案.md`](../02-架构/架构方案.md) §3.2）

所以：**只改客户端连的地址**。这也顺便**验证了接缝 A 不是空话**。

## 2. 宿主选择：T30 取代"云服务器"作为本项目的主机

原来的部署选项只有「Windows 本机 / 阿里云服务器」。现在多了一个**自有常开机器**，而它与云服务器的差别**不是拓扑，是性质**：

| 宿主 | 常开性 | NapCat 登录风控画像 | 成本 | 本项目用它？ |
|---|---|---|---|---|
| **你的 Windows 本机** | ❌ 会关机 | 家庭宽带（正常） | 0 | 开发期可选 |
| **T30（自有塔式服务器）** | ✅ 24h 常开 | **家庭宽带（正常）** | 一次性 | ⭐ **主选** |
| 阿里云服务器（<server-ip-redacted>） | ✅ 24h | **IDC 机房 IP（天然可疑）** | 月租 | ❌ **各管各的**（跑别的） |

### 2.1 ⭐ T30 可能顺带解决一个**真实痛点**

`架构方案.md` §5 的风险清单里，第一条就是：

> **阿里云扫码风控** —— 形态乙/丙直接不可行

**原因**：腾讯风控看**登录 IP 像不像正常用户**。云服务器 IP 段属 IDC 机房，**天然可疑**；而 T30 在你自己家里 → **家庭宽带 IP，风控画像完全不同**。

> ⚠️ **但这是推测，不是结论。** 家宽 IP 只是"看起来更正常"，**没有任何证据**说一定过。
> 依旧需要**一次真实登录验证**（见 §10 的 U1）。

### 2.2 阿里云那台的处置

**各管各的** —— 本项目不再依赖它。相关文档（`NapCat服务器可行性.md`、服务器探针记录）**降为历史存档**，不再作为本项目的部署前提。

> 📌 顺带说明：这件事**对公开面零影响** —— 服务器信息本来就已经划到私有面了。

## 3. T30 落在哪个拓扑形态

拓扑上它属于**「NapCat 与服务端同机」**（原来的形态乙），差别只在宿主是**自有机器**：

| | NapCat | 服务端 | 客户端 | 通道 | 谁常开 |
|---|---|---|---|---|---|
| **形态甲：全本机** | 你的 Windows | 你的 Windows | 同机 | 正向 WS `127.0.0.1` | 你的 Windows |
| **⭐ 形态乙（T30 版）** | **T30** | **T30** | **你的 Windows（走内网）** | 正向 WS **`127.0.0.1`（T30 内部）** | **只有 T30** |
| 形态丙：NapCat 服务器 + 后端本机 | 服务器 | 你的 Windows | 同机 | **反向 WS** | 两台都要 |

**⭐ T30 版形态乙的关键优势**：**服务端与 NapCat 之间仍然是 `127.0.0.1`** ——
也就是说**跨机只发生在"客户端 ↔ 服务端"这一段**，而这一段本来就是 HTTP/WS，设计上早就准备好了。

对比形态丙（反向 WS）要背"两台都常开 + 跨机鉴权"，**形态乙（T30 版）明显更优**。

## 4. ⭐ OS 两条路：详细对比（**用户尚未决定，本节是决策依据**）

### 4.1 总览

| 维度 | **Windows** | **Linux**（Ubuntu/Debian） |
|---|---|---|
| NapCat 安装难度 | 🟢 低 —— 有 Windows 版 / 一键整合包 | 🟡 中 —— 需 Xvfb + 中文字体 + X11 依赖 |
| 扫码登录看得见吗 | 🟢 是（GUI 窗口直接显示二维码） | 🟡 否，但**二维码会落成图片文件**，也可经 WebUI 看 |
| 开机自启 | 🟡 **有坑**（见 4.3） | 🟢 成熟（systemd） |
| 崩溃自动重启 | 🟡 要自己想办法 | 🟢 systemd 原生 |
| 空载内存 | 🔴 ~1.5–2.5 GB | 🟢 ~0.3–0.6 GB |
| 长期常开稳定性 | 🟡 一般（更新会重启、可能弹窗） | 🟢 好 |
| 远程管理 | 🟡 RDP（⚠️ 有副作用，见 4.3） | 🟢 SSH，无副作用 |
| **WinUI3 客户端能否同机跑** | ✅ **能** → loopback → **免 token** | ❌ **不能** → 必须另一台 Windows → **必须配 token** |
| 你的熟悉度 | 大概率更高 | 需要一点 Linux 基础 |

### 4.2 Windows 路：好在哪、坑在哪

**好处**

1. **NapCat 装起来最省事** —— Windows 版 / 一键整合包，不需要 Xvfb、不需要凑 X11 依赖
2. **扫码登录看得见** —— 二维码就在屏幕上，第一次登录最不容易卡住
3. 客户端可以**同机跑**，走 loopback → **免 token**（少一个配错的地方）
4. 你对 Windows 更熟

**⚠️ 坑（三个都是真的）**

| 坑 | 说明 |
|---|---|
| **① GUI 程序不能做成 Windows 服务** | QQ 客户端需要**交互式桌面会话**。Windows 服务跑在 **Session 0**，**看不到桌面** → QQ 起不来。所以 NapCat **不能**用 NSSM 之类做成服务 |
| **② 因此必须"自动登录"** | 只能靠：**设置自动登录到桌面** + **把 NapCat 放进启动项/计划任务**。代价是**机器上敞开一个已登录的桌面会话**（家用可接受，但不优雅） |
| **③ RDP 管理有副作用** | 远程桌面连上去/断开，会**接管并可能锁定交互式会话**，对 GUI 程序的稳定性是个隐患。建议：**连上去别注销**；或用不打扰会话的方式管理 |

### 4.3 Linux 路：好在哪、坑在哪

**好处**

1. **省内存** —— 空载比 Windows 少 **1 GB 以上**（对 8GB 且还要跑别的东西，这条很实在）
2. **自启 / 重启 / 日志是成熟方案** —— systemd unit 三行搞定，不用跟"自动登录"较劲
3. **无 GUI 会话被 RDP 打断的问题** —— SSH 管理，干净
4. 更适合**长期无人值守**
5. **我们有 Xvfb 经验** —— 之前在那台阿里云上装过并保留了 Xvfb

**⚠️ 坑**

| 坑 | 说明 |
|---|---|
| **① 必须 Xvfb** | QQ NT 是 Electron，需要 X display；无头机器上靠 Xvfb 提供虚拟显示 |
| **② 中文字体要装** | 不装字体，QQ 界面/二维码渲染可能出问题 —— 这是最常见的坑 |
| **③ 扫码看不到屏幕** | 但 NapCat 会把二维码**存成图片**，也可经 WebUI 查看 → 实际可行 |
| **④ WinUI3 客户端跑不了** | ⚠️ **必须放到另一台 Windows 机器上** → 跨机连 → **非 loopback → 强制配 token** |

> 📌 **第 ④ 条其实不是问题** —— 你已确认**家里内网能直连**，所以只是"多配一个 token"。
> 而这恰好是鉴权设计第一次真正派上用场（见 §6）。

### 4.4 我的倾向

**倾向 Linux**，理由是三条**具体的、可量化的**：

1. **省 1 GB+ 内存** —— 在 8GB 且**还要跑别的东西**的前提下，这是最实在的一条
2. **自启/重启/日志不用自己发明** —— Windows 那条路的"自动登录 + 启动项"是**在绕系统**，而 systemd 是**顺着系统**
3. **没有"RDP 打断 GUI 会话"这类说不清的隐患**

**但有一条反过来的理由同样成立**：如果你**更看重一次装好**、且**不太熟 Linux**，Windows 路的"看得见二维码 + 不用装 Xvfb"能省掉半天折腾 —— **省下的时间也是成本**。

> ⚖️ **判据**：**如果这台 T30 上"别的东西"也吃内存（Docker / NAS / 媒体服务），选 Linux；如果别的东西很轻、而你不想跟 Xvfb 较劲，选 Windows。**

## 5. ⭐ 8GB 内存总账（**你确认过：还要跑别的东西**）

> ⚠️ 下表的 NapCat/QQ 部分来自**估算**（`进度.md` U2 标注为"未实测，估 400–800 MB"），**不是实测值**。

| 组成 | Windows 路 | Linux 路 |
|---|---|---|
| OS 自身（空载） | ~1.5–2.5 GB | ~0.3–0.6 GB |
| NapCat + QQ | 0.4–0.8 GB | 0.4–0.8 GB |
| Xvfb | — | < 0.05 GB |
| .NET 服务端（Kestrel + Agent + MEAI） | 0.2–0.4 GB | 0.2–0.4 GB |
| **本项目合计** | **≈ 2.1–3.7 GB** | **≈ 0.9–1.8 GB** |
| **留给"别的东西"** | **≈ 4.3–5.9 GB** | **≈ 6.2–7.1 GB** |

**结论**：**8GB 够用**，但两条路的**余量差一倍左右**。

**给"别的东西"的提醒**：

| 若还要跑 | 注意 |
|---|---|
| **Docker** | Linux 下更省（无 Hyper-V 开销）；Windows 下 Docker Desktop 走 WSL2，本身吃 1GB+ |
| **NAS / 文件共享** | 内存不是瓶颈，**但硬盘 IO 会抢** —— 建议本项目的数据与日志放 **SSD** |
| **媒体转码** | 🔴 CPU 会被打满 → 可能拖慢 QQ 心跳与 agent 响应。**别指望跑转码还稳** |
| **再跑一个虚拟机** | 🔴 8GB 基本不够分 |

> 📌 **一条纪律**：**给"别的东西"留至少 1.5 GB 余量。** 内存打满时 Linux 会 OOM-kill，
> 而**被 kill 的很可能是 QQ**（它是最大的进程）→ **表现为"机器人莫名其妙掉线"**，极难查。

## 6. 网络与访问

| 场景 | 做法 |
|---|---|
| **家庭内网（你现在的情况）** ✅ | 服务端监听**内网 IP**（如 `192.168.x.x`），客户端直连 `http://192.168.x.x:5180` |
| **从外网访问**（尚未决定） | ⭐ **推荐组虚拟内网（Tailscale / ZeroTier）** —— 零端口映射、零公网暴露 |
| **服务端 ↔ NapCat（同机）** | 走 `127.0.0.1`，**loopback 免验** ✅ |
| **客户端 ↔ 服务端（跨机）** | ⚠️ **非 loopback → 必须配 `Server.Token`**，否则**拒绝启动**（已定硬约束） |

> 🔴 **红线：绝不要把服务端端口映射到公网。**
> NapCat 的 WebUI 与 OneBot API 都会成为扫描目标，而 QQ 账号一旦被接管，后果比"服务不可用"严重得多。
> 需要外网时，**用虚拟内网，不要用端口映射**。

**为什么 Tailscale 是"天然契合"**：
- 它给你一个**虚拟网卡**，客户端连的是 `100.x.x.x` —— 对服务端来说**仍是"非 loopback"**
  → 所以 **token 那层鉴权仍然生效**（不会因为"用了 VPN"就把鉴权绕过去）✅
- 不需要在路由器上开任何端口

## 7. 开机自启与故障恢复

| 需求 | Linux | Windows |
|---|---|---|
| NapCat 自启 | **systemd unit**（`Restart=always`） | 自动登录 + 启动项/计划任务（⚠️ 不能做服务） |
| 服务端自启 | **systemd unit**（`Restart=always`） | 同上 |
| 崩溃自动重启 | systemd 原生 | 需自己包一层 |
| 断电后恢复 | 主板 BIOS 里设 **AC Power Recovery = On**（否则断电后不会自动开机） | 同左 |
| 网络断了 | NapCat 自动重连（已设计）+ 服务端重试（已设计） | 同左 |

> ⚠️ **BIOS 那条最容易被忘**：不设 `AC Power Recovery`，**家里跳一次闸，机器人就一直躺到你想起来**。

## 9. 备份（**第一版最小方案**）

| 备份什么 | 怎么备 | 频率 |
|---|---|---|
| **SQLite 数据库**（会话/消息/记忆） | 停写 → 复制文件（或 SQLite 在线备份 API）。**别在写入时直接拷** | 每日 |
| **`appsettings.Local.json`**（含机密） | 单独加密保存，**别和数据库放一起** | 改动后 |
| 日志 | 不必长期备份，靠滚动保留（默认 14 天 / 32MB 滚动） | — |

> ⚠️ **SQLite 热拷贝会得到损坏的副本** —— 这是很多人踩过的坑。要么停服务拷，要么用它的备份 API。
