## 1. 目标与范围

### 1.1 目标
构建一个「QQ ↔ DeepSeek」中间件：QQ 侧通过 NapCat（OneBot v11）接入，AI 侧直连 DeepSeek API，agent 循环自行实现。

### 1.2 范围（第一版）

| **不做的** | 多账号并行、分布式/微服务拆分、移动端、DSH 集成、向量检索的复杂实现、UI 美化 |

### 2.2 NapCat 硬事实（2026-09-20 调研）

| 事实 | 内容 | 对架构的影响 | 证据强度 |
|---|---|---|---|
| **反向 WS 官方支持** | NapCat 可作为 WS **客户端**主动连我们的服务端，`url` 字段可为任意可达主机 | ⭐ **跨机部署不需要对方开任何入站端口**——「NapCat 在服务器、后端在本机」不再需要暴露端口 | 强 |
| **Linux 必须 Xvfb** | 不是"纯无显示"，需 `xvfb` + `xauth`，启动形如 `xvfb-run -a qq --no-sandbox` | Linux 部署成本抬高，但官方提供 systemd 模板 | 强 |
| **RHEL10+/CentOS Stream 10+ 无解** | 这些系统 X11 已被移除，官方明言「无法通过 xvfb 实现无头运行，目前没有其他已知方案」 | ⚠️ **服务器必须选 Ubuntu/Debian 系** | 强 |
| **阿里云异地扫码可能被风控** | 官方 issue #931 的案例环境正是「阿里云 Ubuntu 24.04」，扫码提示网络环境异常，改静态 IP / 挂代理均无效，issue 被 `not_planned` 关闭 | ⚠️ **「NapCat 上阿里云」是本方案最大的未验证风险**，必须先行实测 | 强（案例真实） |
| **一实例 = 一 QQ 号** | 官方 collaborator 在 issue #877 明确「napcat 一直没有支持多账号，也不支持账号切换」 | 多账号 = 多实例（多目录 + 多端口），第一版不做 | 强 |
| **连接方式 4 类** | `httpServers` / `httpClients` / `websocketServers`（正向）/ `websocketClients`（反向），配置均为**数组**，可同时启用多个 | 通道层可按需切换，且支持多路 | 强 |
| **鉴权字段 = `token`** | 4 类模式都有 `token`；服务端模式下不配鉴权暴露公网被官方点名「严重安全风险」 | 通道层必须支持 token | 强 |
| **WebUI 默认密码** | v4.8.106 以下为弱默认密码 `napcat`；以上改为启动时随机生成（日志 + 私聊可见） | 本机旧版 4.8.124 已过线；公网部署务必改密或关面板 | 强 |
| **版本漂移** | 本机现装 **4.8.124**（QQ 9.9.22-40768），最新为 **v4.18.28**（建议 QQ 44343+），跨约 10 个 minor | 配置 schema 有变化（如新增 `httpSseServers`），升级需重配 | 强 |

**探针能证明的**：这台 RHEL 8 系机器在**依赖与环境层面完全能承接 Electron 应用**——「不在官方支持列表」不构成硬阻碍。

**探针证明不了的（必须真装真登录才知道）**：
1. **LinuxQQ 的实际内存占用** —— 未安装 QQ，测不到
2. **腾讯风控能否通过** —— 需真实扫码登录（issue #931 的失败案例环境正是阿里云）

**结论**：环境可行性已证实，但真实阻塞点是**内存**与**风控**，二者都无法通过"准备"规避，只能由一次真实登录验证给出判定。

> **副作用记录**：本次探针在服务器上安装了 Xvfb 及其依赖（12 包 / 3.9 MB，2026-09-20 11:32）。未改任何配置、未留 systemd unit、未留常驻进程；自有临时日志已清理。经用户确认，**Xvfb 保留**。

### 2.5 Lagrange.Core 实测结论（放弃原因）

2026-09-21 在 `D:\temp\LagrangeDemo\` 写了嵌入式 demo（net8.0 + `Lagrange.Core` 2.1.1）并真机实测：

| 关卡 | 结果 |
|---|---|
| 引用 NuGet + 编译 | ✅ 0 错误 0 警告 |
| `BotContext` 创建 / 连接腾讯服务器 | ✅ |
| 生成二维码（`Url` + PNG `byte[]`） | ✅ |
| 手机扫码识别 | ✅ |
| 扫码状态上报 | ✅ |
| **腾讯授权** | ❌ **被拒**（手机端提示「扫码授权失败，请前往 QQ 官网下载最新版 QQ 后重试」） |

**根因**：`Lagrange.Core` 的签名白名单内含 `ConnAuthSvr.fast_qq_login` / `get_app_info` / `get_auth_api_list` 等**登录必需命令** → **没有白名单签名 token 必然被拒**。而 token 需走「QQ + GPG 进群申请」流程（每 GitHub 账号最多绑 3 个 QQ），且该签名服务是**有停机前科的第三方单点依赖**（v1 中央 SignServer 曾于 2025-10-10 下线）。次要因素：内置协议版本 `3.2.26-46494` 落后于最新 Linux QQ `3.2.32`。

**技术结论**：嵌入形态本身完全成立（无需 QQ 客户端 / Xvfb / NapCat，二维码可经网络传输）；**唯一门槛是签名白名单**。用户判定「为省内存而引入一层不可控的准入依赖」不划算，故改回 NapCat。

## 3. 架构设计

### 3.1 分层

```
┌──────────────────────────────────────────────┐
│ ① 表现层  管理客户端（Windows 桌面）             │
│    状态 · 配置 · 日志 · 会话 · 手动操作          │
└──────────────────┬───────────────────────────┘
                   │ ★接缝 A：HTTP（单端点+payload，非 REST）+ WebSocket
                   │   （本机走 127.0.0.1，远程走域名/Tailscale）
┌──────────────────┴───────────────────────────┐
│ ② 编排层（服务端，跨平台）                       │
│   · QQ 通道适配    ★接缝 B                     │
│   · 会话路由（群/私聊 → 独立 session）           │
│   · 权限门禁      ★接缝 C（危险操作仅管理员）      │
│   · 主动行为调度（定时 / 群监听）                 │
│   · 记忆服务（长期记忆 / 知识库）                 │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────┴───────────────────────────┐
│ ③ agent 核心层（手写）                          │
│   · agent 循环 · 工具注册与执行 · 上下文管理与压缩 │
│   · LLM 客户端（DeepSeek API，流式）             │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────┴───────────────────────────┐
│ ④ 存储层  会话/消息 · 记忆 · 配置（SQLite）      │
└──────────────────────────────────────────────┘
```

### 3.2 三个接缝（本方案的核心设计）

| 接缝 | 设计 | 为什么这么做 |
|---|---|---|
| **A. 表现层 ↔ 编排层** | **双通道**：① **命令通道 = HTTP（非 REST）**——单端点收 `{action, payload}`、回 `{code, data}`；② **事件通道 = WebSocket**——服务端主动推送日志/消息/状态/二维码。两者同进程内由 Kestrel 承载，客户端始终走网络（本机即 `127.0.0.1`） | ⭐ **让"本机单体"与"服务器分离"共用同一套代码**——切换部署形态只改地址，非重写。**选 HTTP+WS 而非 gRPC**：零额外依赖、`curl` 可直接调试、payload 灵活；代价是弱类型契约需自行维护 DTO |
| **B. QQ 通道 ↔ 编排层** | 抽象为 `IQQChannel` 接口，提供**正向 WS 客户端**与**反向 WS 服务端**两个实现 | 覆盖「NapCat 同机」与「NapCat 跨机」两种拓扑；NapCat 换代（如 LuckyLilliaBot）时上层不动 |
| **C. 工具执行 → 权限门禁** | 工具注册时携带权限元数据（`RequiredRole`），执行前统一过门禁 | ⚠️ **安全边界，不能事后补**。危险操作（执行命令、写/删文件、访问外部服务）默认仅管理员可用 |

### 3.3 部署形态

> ⚠️ **两个维度要分开**：**拓扑形态**（谁跑在哪台机器）与**宿主性质**（那台机器是什么）。
> 2026-09-22 新增一台**自有常开服务器（T30，8GB）** → 它**拓扑上属形态乙**，但**宿主性质**是"自有常开机"，**风控画像与云服务器完全不同**。
> **完整分析见 [`03-设计/部署设计.md`](../03-设计/部署设计.md)。**

| | 形态甲：全本机 | ⭐ **形态乙（T30 版）** | 形态丙：NapCat 服务器 + 后端本机 |
|---|---|---|---|
| NapCat | Windows 本机 | **T30** | 服务器 |
| 服务端 | Windows 本机 | **T30** | Windows 本机 |
| 客户端 | 同机 | **你的 Windows（走内网）** | 同机 |
| 通道 | 正向 WS（127.0.0.1） | 正向 WS（**T30 内部 127.0.0.1**） | **反向 WS** |
| 谁常开 | 你的 Windows | **只有 T30** | **两台都要** |
| 宿主性质 | 家用机（会关机） | **自有常开 + 家庭宽带 IP** | 视 ISP/机房而定 |
| 前置成本 | 最低（OneKey 包内置 QQ） | NapCat 需 Xvfb（Linux）或自动登录（Windows） | 兼有两边成本 |
| 风险 | 本机关机即离线 | **家宽扫码风控（待实测）** | 网络依赖 + 跨机鉴权 |

**评价**：
- 形态甲 = 开发与自用最省事，但**群友 @ 时机器关着会失联**
- ⭐ **形态乙（T30 版）= 当前主选**：可用性高、**跨机只发生在"客户端 ↔ 服务端"这一段**（本来就是 HTTP/WS，设计已备好）、代码与形态甲**完全相同**（只改配置）、且**家宽 IP 的风控画像比云服务器正常**
- 形态丙 = 反向 WS 让它技术上可行，但把「两台机器都得常开」+「跨机鉴权」的复杂度都背上了，收益不明确

> **阿里云服务器（8.141.89.50）：已决定"各管各的"**，本项目不再使用。相关评估文档降为历史存档。

### 3.4 技术选型（已定稿 · 2026-09-22 更新）

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **.NET 10**（LTS） | 跨平台，满足 Windows/Linux 双兼容要求。用户既定：新项目一律 .NET 10 |
| 服务端宿主 | `Microsoft.Extensions.Hosting` + ASP.NET Core（Kestrel） | 同进程内提供 **HTTP（命令）+ WebSocket（事件）**；可作为 Windows 服务 / Linux systemd / Docker 运行 |
| **客户端通信** | **HTTP 单端点（非 REST）+ WebSocket**，**不引 gRPC** | 命令走 HTTP：`POST` 单端点，body 为 `{action, payload}`，响应 `{code, data}`；事件走 WS 推送。零额外依赖、`curl` 可调试；客户端为 WPF，无需浏览器兼容性 |
| **表现层** | **WPF**（Windows-only，仅表现层） | ✅ **已定（2026-09-20，D2）**。客户端为 WPF 不影响服务端跨平台 —— 见 §3.2 **接缝 A**（表现层走 HTTP/WS，与服务端解耦） |
| **AI 框架** | **MEAI（`Microsoft.Extensions.AI`）打底 + 部分自研**，**不引 MAF** | 自动工具循环（`FunctionInvokingChatClient`）、OpenAI 兼容端点接入（`Microsoft.Extensions.AI.OpenAI`）用现成；**会话隔离 / 上下文压缩 / 工具权限门禁 / `AgentEvent` 流自研**。详见 [`03-设计/Agent设计.md`](../03-设计/Agent设计.md) |
| LLM 端点 | DeepSeek（OpenAI 兼容格式） | 经 MEAI 的 OpenAI 适配器接入；**不绑死 DeepSeek**，换任何 OpenAI 兼容端点只改配置 |
| **JSON** | **`System.Text.Json`（全项目统一）** | 与 MEAI **同栈**，避免双 JSON 库；`JsonNode` 可承载动态事件载荷。原 Newtonsoft 方案已废弃 |
| 存储 | SQLite（EF Core 或 Dapper） | 跨平台、零运维；会话/记忆/配置同库或分库 |
| 检索 | SQLite FTS5（全文）+ 可选的向量余弦相似度 | 第一版不做复杂向量库 |
| **配置** | **JSON**：`appsettings.json` + `appsettings.Local.json`（+ 环境变量 + 命令行） | ✅ **定稿（2026-09-22）**：用 .NET 原生 `Microsoft.Extensions.Configuration.Json`，**零额外依赖**。<br>⚠️ **YAML 曾评估并否决**：.NET **原生不支持 YAML**，要用就得引第三方包，而事实标准的 `NetEscapades.Configuration.Yaml` **2023-04 后停更三年**、且拖着的 `YamlDotNet` 底线落后 5 个大版本。详见 `07-记忆/决策记录.md` |
| 日志 | Serilog | 结构化、可轮转、可推送客户端 |
| 测试 | xUnit | .NET 标准 |

> 💡 **一个容易搞错的地方（2026-09-22 查证 .NET 源码）**：**配置文件里能不能写注释，取决于走哪条管线**。
>
> | 哪条管线 | 注释 | 尾逗号 |
> |---|---|---|

> | **直接用 `JsonSerializer`**（DTO / 契约测试） | ❌ **默认拒绝** | ❌ 默认拒绝 |
>
> → **所以手写的 `appsettings.json` 可以放心带 `//` 注释**；
> → 而 [`docs/05-契约/`](../05-契约) 里的样例用的是 **`"_comment"` 数据字段**而不是 `//` —— **那个设计是对的**（契约测试走 `JsonSerializer` 那条管线）。

| **C. 工具执行 → 权限门禁** | **`GuardedAIFunction`** —— 包在 `AIFunction` 外侧的装饰器，权限判定 / 超时 / 异常隔离 / 输出截断 | 见 [`03-设计/Agent设计.md`](../03-设计/Agent设计.md)。**门禁在服务端** |

### 3.5 通信契约（草案 · 2026-09-21 用户确认分工与鉴权）

**职责分工（已定）**：HTTP **只发命令**（客户端主动、请求-响应）；WebSocket **只收事件**（服务端主动推送）。两者不重叠。

**① HTTP 命令通道（非 REST）**

```
POST /api
Header  : Authorization: Bearer <token>      ← 仅当监听非 loopback 时要求
Body    : { "action": "<动作名>", "payload": { ... } }
Response: { "code": 0, "message": "ok", "data": { ... } }
```

- **不用 REST 路径风格**（不做 `GET /sessions/{id}` 之类），一律 `POST /api` + payload 里的 `action`
- `code = 0` 表示成功；非 0 为业务错误，`message` 带说明
- 预期动作（草案，待细化）：`ping`、`getStatus`、`getConfig` / `saveConfig`、`listSessions` / `getSession` / `getMessages`、`sendMessage`、`restartQQChannel`、`listTools`

**② WebSocket 事件通道**

```
WS  /events
Header  : Authorization: Bearer <token>      ← 仅当监听非 loopback 时要求
```

服务端推送帧格式：

```
{ "type": "<事件类型>", "seq": <服务端递增序号>, "time": <unix ms>, "data": { ... } }
```

预期事件类型（草案）：

| type | 说明 |
|---|---|
| `hello` | 连接建立时下发服务端信息（版本 / 能力） |
| `qq/state` | QQ 通道状态：`connected` / `disconnected` / `connecting` |
| `qq/qrcode` | 登录二维码（`url` + PNG base64） |
| `qq/message` | 收到或发出的 QQ 消息 |
| `log` | 服务端日志流 |
| `session/update` | 会话状态变化（新建 / 更新） |

- 客户端**断线自动重连**；用 `seq` 判断是否丢帧（丢帧时可选择主动补拉）

**③ 鉴权（已定）**

| 监听地址 | 要求 |
|---|---|
| 仅 loopback（`127.0.0.1`） | **免验** |
| 非 loopback（服务器 / Tailscale / 公网） | **强制 token**（HTTP 走 `Authorization` 头；WS 同时支持首帧鉴权） |

> ⚠️ **安全边界**：监听地址一旦不是 loopback，**启动时必须校验 token 已配置**，否则拒绝启动——避免"忘了配 token 就裸奔"。

## 4. 里程碑与验收标准（草案）

| # | 里程碑 | 验收标准（可判定） |
|---|---|---|
| M1 | 链路打通 | NapCat 收到私聊/群消息 → 服务端解析 → 调用 DeepSeek → 回复送达 QQ；真机收发验证通过 |
| M2 | 会话隔离 | 不同群、同群不同用户、私聊，三者的上下文互不串；重启后会话可恢复 |
| M3 | 多角色人格 | 可通过配置切换人格，且切换后 system prompt 生效（**须验证旧项目 `System` 被降级为 `assistant` 的 bug 不复发**） |
| M4 | 工具调用 | 至少 1 个工具（如时间查询/联网搜索）能被模型正确调用并回填结果；工具异常不导致会话崩溃 |
| M5 | 权限门禁 | 非管理员触发危险工具 → 被拒绝并留痕；管理员触发 → 成功；**有对应用例** |
| M6 | 长期记忆 | 跨会话记住指定用户信息，并在新会话中正确召回 |
| M7 | 主动行为 | 定时任务按配置触发主动发言；群监听模式下按规则自主响应 |
| M8 | 管理后台 | 客户端可查看会话列表/消息/日志，可修改配置并生效 |
