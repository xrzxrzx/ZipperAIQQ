## 1. 这个项目是什么

一个**对接 QQ 与 LLM 的中间件**。服务端要连三样东西：

| 连接对象 | 协议 | 说明 |
|---|---|---|
| **平台通道** | QQ：OneBot 11 over WebSocket；抖音：Node sidecar（`/ws/channel`）；邮件：IMAP | 平台无关抽象是 `IMessageChannel` / `IMessageSource`；QQ 只是首个实现 |
| **LLM** | OpenAI 兼容 HTTP API | **不绑死某一家**——只要兼容 OpenAI 格式，换端点只改配置 |
| **管理客户端** | HTTP（命令）+ WebSocket（事件） | WinUI3 桌面程序，看状态 / 看日志 / 发消息 |

**一句话**：QQ 消息进来 → 交给 agent（带工具、带上下文）→ 回复发回 QQ；
同时把「正在想什么、调了什么工具」实时推给桌面客户端。

### 1.1 外部项目依赖（**不在本仓库**）

本项目只写**适配层**，下面两个第三方项目需要单独获取、部署：

| 项目 | 角色 | 接入方式 | 注意 |
|---|---|---|---|
| **NapCat**（[NapNeko/NapCatQQ](https://github.com/NapNeko/NapCatQQ)） | QQ 协议端（OneBot 11） | 服务端作为**正向 WS 客户端**连它（`NapCatChannel`） | 必须开 `access_token`；许可与使用条款以上游为准 |
| **douyin-im**（[xrzxrzx/douyin-im](https://github.com/xrzxrzx/douyin-im)，MIT） | 抖音协议库（Node / TypeScript） | `douyin-sidecar/` 以 npm 依赖引入，跨进程通过 `/ws/channel` 接入 | **不 vendor、不用 submodule**；建议锁 commit |

> - 上游项目的问题提到各自仓库；本仓库只维护 `NapCatChannel` / `douyin-sidecar` 这些适配代码。
> - 不用抖音时不需要 douyin-im / Node；纯 QQ 部署只需要 NapCat。

## 2. 分层与项目划分

```
ZipperAIQQ.slnx                 （仓库根目录，项目之间平级）
├── ZipperAIQQ.Core/            ⓪ 横切关注点（事件总线 / 北京时间）
├── ZipperAIQQ.Transport/       ① WebSocket 传输封装（正向连接）
├── ZipperAIQQ.Channel/         ② 平台无关通道抽象 + NapCat 实现
├── ZipperAIQQ.Storage/         ③ SQLite 持久化
├── ZipperAIQQ.Mail/            ④ IMAP 收信（只收不发）
├── ZipperAIQQ.Agent/           ⑤ AI 编排（工具循环 / 记忆 / 权限门禁）
├── ZipperAIQQ.Server/          ⑥ 服务端宿主 + 组合根（Kestrel：HTTP + WS）
├── ZipperAIQQ.Client/          ⑦ WinUI3 客户端（⚠️ 唯一 Windows-only）
└── ZipperAIQQ.Tests/           ⑧ xUnit 测试（全部项目共用）
```

| # | 项目 | 职责 | 关键类型 |
|---|---|---|---|
| ⓪ | **Core** | **横切关注点**：进程内事件总线、北京时间转换。**⚠️ 准入规则见下** | `IEventBus` / `EventBus` / `BeijingTime` |
| ① | **Transport** | WebSocket 的**通用能力**：建连、收发、关闭。**接口用 `JsonNode`，与业务无关**；服务端自身的 HTTP/WS 端点由 Kestrel 直接承载，不经过它 | `IWebSocketTransport` / `ClientTransport` / `WebSocketDuplexBase` |
| ② | **Channel** | 平台无关的消息抽象 + 各平台实现。QQ 的 OneBot 11 解析在 `NapCat/` | `IMessageChannel` / `IMessageSource` / `NapCatChannel` / `CompositeMessageChannel` / `OneBotEventMapper` |
| ③ | **Storage** | SQLite（`Microsoft.Data.Sqlite` 手写 SQL）：消息 / 会话 / 记忆 / 配置 / 邮件 / 定时任务 | `ISqliteDatabase` / `SqliteMessageStore` / `DatabaseInitializer` |
| ④ | **Mail** | IMAP 收信（**只收不发**）：账号连接、增量拉取、摘要数据 | `MailSource` / `MailAccountSession` / `IMailRepository` |
| ⑤ | **Agent** | AI 编排：工具循环、会话隔离、上下文压缩 / 检索、权限门禁、事件流 | `ChatAgent` / `ExecutionPolicy` / `PermissionGate` / `MemoryRetriever` / `SummaryService` |
| ⑥ | **Server** | 宿主 + **唯一组合根**；Kestrel 端点（`/api`、`/events`、`/ws/ext`、`/ws/channel`）、消息路由、命令、定时任务、邮件管道 | `Program` / `ServiceRegistration` / `MessageRouter` / `ActionDispatcher` |
| ⑦ | **Client** | WinUI3 界面（MVVM）。**自己维护一份 wire DTO** | `Views/` / `ViewModels/` / `Services/` / `Dto/` |
| ⑧ | **Tests** | xUnit；覆盖通道解析、存储、Agent 纯逻辑、Server 逻辑、邮件与抖音通道 | `ZipperAIQQ.Tests/` |

> ### ⚠️ `Core` 的准入规则（**放东西进去之前请先读**）
>
> **两条都要满足：**
>
> **判据一 —— 能说出第二个消费者是谁。** 说不出来就别放。
>
> **判据二 —— 它是「横切关注点」，不是「运行时能力」。**
>
> | | 是什么 | 例子 | 进 Core？ |
> |---|---|---|---|
> | **横切关注点** | **每个模块都要用**，本身**不是功能**，是所有功能都需要的背景设施 | 事件总线、时间换算 | ✅ |
> | **运行时能力** | **某些模块为了干某件事**才需要，它本身**是一个功能** | `Transport`（连网络）、`Storage`（存数据）、配置装载（Server 组合根负责） | ❌ |
>
> > ⭐ **最准的一句判据**：**「把所有业务模块删光，这东西还需要吗？」**
> > 事件总线要、时间换算要；**WebSocket 连接、数据库、配置装载就不要了** —— 所以后三个**不进 Core**。
>
> | ✅ 可以放 | ❌ 不许放 |
> |---|---|
> | 跨模块共用的**横切设施** | 有业务语义的东西（会话、消息、人格…） |
> | **无业务语义**的抽象与薄适配 | 只服务单一模块的代码 |
> | 通用守卫 / 结果类型（出现 ≥2 个消费者 + 是横切） | **跨进程 wire 契约**（HTTP / WS 的 DTO —— 归各模块自己的 `DTO/`） |
>
> **为什么定这条**：`Core` / `Common` 这类项目**天然会变成垃圾桶** —— 谁都觉得"这个挺公共的"就塞进来。
> 没有准入规则，半年后它会依赖所有人、也被所有人依赖，改一行炸一片。
>
> （**2026-09-22 补记**：判据二是后加的一条 —— 原本只有判据一，结果发现 `Transport` 也能通过，规则太宽。）

> 📌 **为什么没有 `ZipperAIQQ.Contracts` 项目**：客户端与服务端**各自维护 DTO**，
> 一致性靠 [`docs/05-契约/`](../05-契约) 的样例 + CI 的机械校验（JSON 合法 / 身份字段占位 / 链接不断）来兜。
> ⚠️ 「两端各写一个断言测试」**目前还没有接入**（见 `docs/05-契约/README.md`），所以改契约时要人工对照样例。
> 代价是编译器帮不上忙，收益是省掉一层最容易写漏的映射代码。

## 3. ⭐ 三个不可破坏的接缝

这三条是这个架构**存在的理由**。改动时如果发现自己在绕过它们，**先停下来开 issue 讨论**。

### 接缝 A：表现层 ↔ 编排层 —— 必须走 HTTP / WS

**不许进程内直连。**

> **为什么**：这个项目有两种部署形态 —— ① **本机单体**（客户端和服务端同一台机器）
> ② **服务端分离**（服务端跑在别处）。
> 两者**共用同一套代码**，靠的就是"A 永远走网络"。
> 一旦有人为了"省一次序列化"直连进去，形态 ② 立刻坏掉，而且是**运行期才发现**。

### 接缝 B：QQ 通道 ↔ 编排层 —— 必须经 `IMessageChannel`

**上层不得直接依赖 NapCat / OneBot 的类型。**

> **为什么**：NapCat 是**第三方协议端**，它会变、也可能被换掉。
> `Agent` 只需要知道"有消息进来、有事件出去"，**它不该知道 QQ 的存在**。

### 接缝 C：工具执行 → 权限门禁 —— 门禁在服务端，默认仅管理员

**危险操作（执行命令、写 / 删文件、访问外部服务）默认只有管理员能触发。**

> **为什么**：LLM 是不可信输入源 —— 群友可以让它"帮忙删个临时文件"。
> 所有工具都要在 `ToolCatalog` 登记，并由 `ExecutionPolicy` / `PermissionGate` 在**每次构建工具列表时**统一判定权限；
> 工具内部把异常转成给模型看的失败原因（不要假装成功）。
> ⚠️ **不许存在绕过门禁的注册路径**（`ToolCatalog` 是唯一登记处）。

## 4. 依赖方向（硬约束）

```
  第 0 层          ⓪ Core               横切关注点：事件总线 / 时间
                   ① Transport          WebSocket 封装（接口用 JsonNode，与业务无关）

  第 1 层          ② Channel（→ ① ⓪）     ③ Storage（→ ② ⓪）
                   ④ Mail（→ ③ ② ⓪）

  第 2 层          ⑤ Agent（→ ② ③ ⓪）    AI 编排；不依赖 Server

  第 3 层（组合根） ⑥ Server（→ 全部）      ⑦ Client（无内部项目引用，独立维护 wire DTO）
```

**五条不可破坏的约束**：

1. **`Core` 不得引用任何其他内部项目** —— 它是横切层，引用任何业务项目都会立刻循环
2. **除 `Client` 外，任何项目都不得引用 WinUI3 / Windows 专有程序集**
   ⟶ 这是「**服务端跨平台**」的物理保障。**Linux 上除 Client 外的项目必须能构建通过**
3. **`Agent` 不得依赖 `Server`，也不得直接使用 NapCat / OneBot 类型** —— agent 只认 `IMessageChannel`
4. **上层不得依赖 `Transport` 的具体实现**：服务端只用 `IClientTransport` 连 NapCat，
   **服务端自己的 HTTP / WS 端点由 Kestrel 直接承载**
5. **客户端与服务端各自维护 DTO** —— 契约一致性靠纪律 + `docs/05-契约/` 样例，编译器帮不上忙

> ⚠️ **第 5 条是这个项目最容易踩的坑**：客户端和服务端各写一份同名 DTO，改了一边，
> **编译期不会提醒另一边**（契约是 JSON，跑到那一步才发现）。
> **补法**：[`docs/05-契约/`](../05-契约) 里的 JSON 样例 + CI 的机械校验。
> ⚠️ 「两端各写一个断言测试」**尚未接入**，所以改契约时必须人工对照样例。

## 5. 通信契约

**职责分工**：HTTP **只发命令**（客户端主动，请求-响应）；WebSocket **只收事件**（服务端主动推送）。**两者不重叠。**

```jsonc
// ① HTTP 命令：POST /api
//    Header: Authorization: Bearer <token>   ← 仅当监听非 loopback 时要求
请求  { "action": "<动作名>", "payload": { ... } | null }
响应  { "code": 0, "message": "ok", "data": { ... } | null }

// ② WebSocket 事件：WS /events 上的每一帧
{ "type": "<事件类型>", "seq": <int64>, "time": <int64 unix ms>, "data": { ... } | null }
```

- **不用 REST 路径风格**（没有 `GET /sessions/{id}` 这种），一律 `POST /api` + payload 里的 `action`
- `code = 0` 表示成功，非 0 为业务错误（`message` 带说明）
- `seq` **服务端单调递增**，客户端用它判断是否丢帧
- **鉴权**：loopback 免验；**非 loopback 必须配 token，未配则拒绝启动**（`HttpAccessPolicy` 构造时校验）

> 另有两条独立端点：`/ws/ext`（外部接口协议）与 `/ws/channel`（抖音 sidecar 反向接入），
> **不复用** `/events` 的事件帧格式 —— 三者各自的样例/约定见 `docs/05-契约/` 与对应设计文档。

**权威清单**：[`docs/05-契约/`](../05-契约) 里的样例文件 + 那份 README。

## 6. 一条 QQ 消息的旅程

```
QQ 用户发消息
   │
   ▼
[NapCat] ──OneBot 11 正向 WS──▶ ② NapCatChannel（Channel 项目）
   │
   ▼
⑥ Server 的消息编排（MessageRouter）
   ├─ 解析：谁发的、群还是私聊、@ 了没
   ├─ 定位会话：SessionId = "qq:g<群号>" 或 "qq:p<QQ号>"
   ├─ 接收过滤 + 权限判定：QQ 号 → 主人 / 管理员 / 白名单 / 普通
   └─ 回复模式：every / mention / jev
   │
   ▼
⑤ ChatAgent.RunAsync
   ├─ 取该会话上下文（热窗 + 摘要 + 向量检索）
   ├─ 锚点 system(人设) + 重注入 system + 历史 + 新输入
   └─ 工具循环：LLM ⇄ 工具（经 ExecutionPolicy / PermissionGate）
        └─ 产出 AgentEvent 流
   │
   ├────────────▶ （旁路）⑥ EventBroadcaster ──WS /events──▶ ⑦ WinUI3 客户端
   ▼
⑥ 出站：ThrottledMessageChannel（全局节流）→ NapCatChannel 发送
```

> 多平台下 `SessionId` 带平台段（`douyin:p<id>` / `qq:g<id>`），
> `MessageRouter` 按平台分发给对应通道（`CompositeMessageChannel` 负责路由与故障隔离）。

## 8. 我要改 XX，该动哪里？

| 你想做的事 | 动哪里 | 注意 |
|---|---|---|
| **加一个服务 / 接口实现** | `Server/Composition/ServiceRegistration.cs` 的 `AddZipperServices`（**唯一组合根**） | ⚠️ 不要把 `new` 散到别处 |
| **需要"启动时连什么"** | 实现 `IHostedService`（异步运行期任务）；启动前校验放在构造期（如 `HttpAccessPolicy`） | ⚠️ 注册阶段（`Add*`）不许做 I/O |
| **加一个给 AI 用的工具** | `Agent/Tools/` 新增一个类 + 在 `ToolCatalog` 登记 + `ServiceRegistration` 注册 | 🟢 **最适合新手**；`description` 要写"**何时使用**" |
| **加一个配置项** | `Server/Configuration/ServerOptions` + `ServerConfigLoader`（YAML 优先）+ 环境变量兜底 | ⚠️ **含密的项绝不许写进仓库**；日志里**脱敏** |
| **加一个 HTTP 命令** | `Server/Api/Handlers/` 实现 `IApiAction` + `ServiceRegistration` 注册 + **两端 DTO**（`Server/Dto`、`Client/Dto`） | ⚠️ action 名是契约；别忘了 `docs/05-契约/` 加样例 |
| **加一个 WS 事件** | `Server/Api/EventBroadcaster` + 两端 DTO | 同上 |
| **改平台协议（QQ）** | `Channel/NapCat/` | 别把 OneBot 类型泄到上层 |
| **改平台协议（抖音 / 邮件）** | `Server/Channels/`、`Mail/` | 通道层实现 `IMessageChannel` / `IMessageSource` |
| **改 AI 行为 / 人格 / 上下文策略** | `Agent/`；提示词在 `SystemPrompts` / `PromptRules` | 影响面大，先开 issue |
| **改桌面界面** | `Client/` | 🟡 中等门槛；VM 要能单测（不依赖 UI 类型） |
| **改 WebSocket 收发** | `Transport/` | 🔴 **高危**：分帧、并发发送、关闭握手，**先讨论** |
| **改权限门禁** | `Agent/Security/`（`ExecutionPolicy` / `PermissionGate`） | 🔴 **安全相关，必须 maintainer review** |
| **改配置装载 / 日志** | `Server/Configuration/`、`Server/Composition/ObservabilityRegistration` | 🔴 **安全相关**（脱敏、机密回显） |
| **想往 `Core` 加东西** | —— | ⚠️ **先说出第二个消费者是谁 + 它是否横切**，说不出来就别放（见 §2） |

> ⚠️ **组合根只有一处**：`Server/Composition/ServiceRegistration.cs`。
> 以前文档里写的"每个模块自己的 `AddXxx`"**并未落地**，不要照着找。

**危险区清单**见 [`CONTRIBUTING.md`](../../CONTRIBUTING.md)。

## 9. 术语表

| 词 | 含义 |
|---|---|
| **NapCat** | 第三方 QQ 协议端（**非官方**），对外暴露 OneBot 11 接口 |
| **OneBot 11** | 一套 QQ 机器人应用层协议：事件用 WS 推、调用用 WS/HTTP 发，靠 `echo` 字段配对请求-响应 |
| **正向 / 反向 WS** | 正向 = 我们主动连 NapCat / sidecar；反向 = 对方主动连我们（如抖音 sidecar 连 `/ws/channel`） |
| **MEAI** | `Microsoft.Extensions.AI`，微软的 AI 抽象层（`IChatClient` 等） |
| **`FunctionInvokingChatClient`** | MEAI 提供的中间件：**自动完成"调 LLM → 执行工具 → 回填结果 → 再调 LLM"这个循环** |
| **接缝（seam）** | 见 §3 —— 三条不许绕过的边界 |
| **会话（Session）** | 一段独立的对话上下文，`SessionId` 形如 `qq:g<群号>`（群）或 `qq:p<QQ号>`（私聊）；多平台下前缀换成平台码 |
| **门禁（Gate）** | 工具/命令执行前的权限判定：`ExecutionPolicy` + `PermissionGate`，见接缝 C |
| **`Core`** | 横切关注点项目（事件总线 / 时间）。**有准入规则**，见 §2 |
| **事件总线** | 进程内发布订阅（`IEventBus`）。让通道层发事件时**不需要知道谁在听** |
| **Options** | 配置的强类型映射；**跟着消费者模块走**，不集中在 `Core`（服务端在 `Server/Configuration`） |
| **组合根（Composition Root）** | **唯一**装配依赖注入容器的地方：服务端 `Program` + `ServiceRegistration`，客户端 `App.xaml.cs` |
