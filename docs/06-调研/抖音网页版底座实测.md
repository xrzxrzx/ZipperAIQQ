### 3.2 登录成功判定（**踩过的坑**）

| 判据 | 结果 |
|---|---|

| ✅ `sessionid` / `sessionid_ss` / `sid_tt` | 登录后才出现，且长度 > 10 |

实测：扫码后三个 cookie 齐 → `phase=logged_in`。

## 5. 帧协议（核心）

### 5.1 传输通道

| 项 | 值 |
|---|---|
| WS 地址 | **`wss://frontier-im.douyin.com/ws/v2`** |
| 帧形态 | 控制帧是文本（心跳 `"hi"`，2 B）；业务帧是**二进制 protobuf**（1.2–2.8 KB 常见） |
| 可观测性 | Playwright `page.on('websocket')` + `framereceived` **能拿到原始字节**（已落盘 `out/bodies/ws-0NN.bin`） |

### 5.2 外框：`im_proto.Frame`

用 `douyin-im` 自带的 `lib/services/im/proto/im.proto` 解码（`protobufjs`）：

| 字段 | 号 | 实测值示例 |
|---|---|---|
| `seqid` | 1 | `<seqid>`（实测为 9 位数字） |
| `logid` | 2 | `<logid>`（实测为 19 位数字） |
| `service` | 3 | **5 / 20003 / 20313**（见下） |
| `method` | 4 | `1` |
| `headers[]` | 5 | `x_frontier_arriverate`、`x_frontier_recieved_time`、`:x_frontier_msg_id`、`:x_frontier_msg_send_time`、`x_frontier_traceid`、`traceparent` |
| `payload` | 8 | 二进制（按 service 分三种形态） |

> **`:x_frontier_msg_id`** 形如 `msg_<opaque-id>`，**可直接做幂等键**。

### 5.3 按 `service` 分流（三类 payload）

| service | payload 形态 | 是什么 | 解码方式 |
|---|---|---|---|
| **5** | protobuf | 私信消息 | `im_proto.Response` → `body.hasNewMessageNotify.message` |
| **20003** | **纯 JSON** | 评论 / @ 等互动消息 | `JSON.parse(payload)` |
| **20313** | 纯 JSON | 未读计数 | `JSON.parse` → `notice_count[]` |

#### 5.3.1 `service=5`：私信

```
Frame.payload
 └ im_proto.Response { cmd=500 (NEW_MSG_NOTIFY), sequenceId, statusCode, body }
    └ body.hasNewMessageNotify {
         conversationId, conversationType, notifyType,
         message { serverMessageId, indexInConversation, conversationShortId,
                   messageType, sender, content(JSON 字符串) }
      }
```

实测样本（同一会话 `0:1:<uid-peer>:<uid-self>`）：

| 帧 | `messageType` | `sender` | `content` 解析 |
|---|---|---|---|
| ws-016 | **5** | <uid-peer> | `{"aweType":507,"display_name":"比心","emoji_type":"lite_emoji",…}`（表情包） |
| ws-018 | **7** | <uid-peer> | `{"aweType":700,"text":"<示例文本>",…}`（文本） |
| ws-045/046 | **50001** | <uid-self> | `MESSAGE_TYPE_COMMAND` —— **命令型事件，必须丢弃** |

`messageType` 实测表：

| 值 | 含义 | 处理 |
|---|---|---|
| 5 | 表情（`lite_emoji` / `display_name`） | ✅ 进事件（标注为表情） |
| 7 | 文本（`content.text`） | ✅ 进事件 |
| 8 | 分享卡片·**作者**（`aweType=800`，`content_name`） | 可进事件（当文本） |
| 105 | 分享卡片·**视频**（`aweType=10500`，含 **`itemId`**、`aweme_title`、`aweme_author_id`、`cover_url`、`comment`） | ✅ 进事件，并把 `itemId` 带下去 |
| 50001 | `MESSAGE_TYPE_COMMAND`（内部命令） | ❌ 丢弃 |

#### 5.3.2 `service=20003`：评论 / @

`JSON.parse` 后的字段（实测两条）：

```
notice_id_str, title(昵称), title_en, from_uid, from_sec_uid,
content, content_en, open_url, comment_id, item_id, notice_type,
push_type, inapp_push_type, image_url, extra{can_comment,comment_permission_status,level,parent_id},
available_in_activity
```

| 事件 | `content` | `notice_type` | `push_type` | `inapp_push_type` | `open_url` |
|---|---|---|---|---|---|
| 提到了你 | `<b>提到了你：</b>@<机器人昵称> 测试` | **45** | 7 | 4 | `sslocal://notification?label=comment_at&…` |
| 评论了你 | `<b>评论了你：</b>测试` | **31** | 5 | 2 | `sslocal://notification?label=comment&…` |
| 提到了你（早前） | `<b>提到了你：</b>@<机器人昵称> 在不在` | 45 | 7 | 4 | `label=comment_at` |

> `content` 带 `<b>` 标签 → 入库/进上下文前需剥标签。
> **「主人回复 AI 的评论」属同一族**（`comment` 形态）→ 用 `from_uid == 主人 uid` + `comment_id` 去重即可，不需要新通道。

#### 5.3.3 `service=20313`：未读计数

```
{ back_up, count, msg_id, notice_count[{g,c,dc,s}], notice_count_v2, notices[], notify_group, push_time }
```

只用于角标/健康度，**不进 Agent**。

### 5.6 DOM 是否可靠？（实测反证）

在 `/chat` 里数「消息气泡节点」数量：

```
初始 123 个  →  往上滚（加载历史）216 个  →  滚回底部 123 个
```

⇒ **消息列表是虚拟滚动，离开视口的节点会被卸载**。**纯 DOM 轮询会漏消息**，所以入站主路径必须是 §5.3 的帧/接口，DOM 只做兜底。

## 7. 视频链路

### 7.1 两途径拿 `itemId`

| 途径 | 来源 | 实测 |
|---|---|---|
| **① 评论 / 视频页** | 评论通知里的 `item_id`，或视频页 URL 的 `/video/<id>` | `<itemId-1>` |
| **② 私信 / 群聊分享** | `messageType=105` 的 `content.itemId` | `<itemId-2>` |

### 7.2 取播放地址并下载

```
GET/POST /aweme/v1/web/multi/aweme/detail/?…&aweme_ids=[<itemId>]&origin=0
  → aweme_details[0].video.play_addr.url_list[0..2]   （3 个 CDN，v96-web.douyinvod.com 等）
```

| 样本 | 时长 | 下载 | 文件头 |
|---|---|---|---|
| `<itemId-1>` | 5,934 ms | 1,756,801 B | `00000020 66747970 69736f6d`（`ftyp isom`） |
| `<itemId-2>` | 28,666 ms（576×1120） | 2,532,727 B | 同上 |

下载用 **Playwright 的请求上下文**（`ctx.request.get(url, { referer, user-agent })`），自动带 cookie、绕开页面 CORS。

### 7.3 抽帧（**不用 ffmpeg**）

```js
// 页面内执行
const v = document.querySelector('video');
v.currentTime = t;                       // 精确 seek
await new Promise(r => v.addEventListener('seeked', r, { once: true }));
const c = document.createElement('canvas');
c.width = v.videoWidth; c.height = v.videoHeight;
c.getContext('2d').drawImage(v, 0, 0, c.width, c.height);
c.toDataURL('image/jpeg', 0.85);         // → base64 → 落盘 .jpg
```

实测（28.67 s 视频、N=4）：

| 张 | 时间点 | 大小 |
|---|---|---|
| 首帧 | 0.04 s | 5,666 B |
| 等分 1 | 3.58 s | 37,557 B |
| 等分 2 | 10.75 s | 36,786 B |
| 等分 3 | 17.92 s | 18,222 B |
| 等分 4 | 25.08 s | 46,895 B |

> 5 张 ≈1 秒跑完；**时间点精确、可任意区间**（`start`/`end` 由模型定）。

### 7.4 抽音轨（**不用 ffmpeg**）

```
下载 mp4 → base64 传进页面 → AudioContext.decodeAudioData
  → 混单声道 → 线性重采样 16 kHz → PCM16 → 自封 44 字节 WAV 头
```

实测：`srcRate=44100`、`srcChannels=2`、`duration=28.605 s` → `outSamples=457,680`、**WAV 915,404 B**（= 28.61 s × 16 kHz × 2 B）。

## 8. 人声转写（DeepSeek ASR）

| 项 | 值 |
|---|---|
| 请求 | `POST https://api.deepseek.com/v1/tools/asr`，multipart `file=@16k.wav` |
| 实测 | **200**，耗时 **2,315 ms**，`{"text":"知り合いの娘は僕のセリフだ。…","duration_ms":28605}` |
| 硬限制 | **≤120 秒 / ≤8 MiB / 非流式** → 长视频必须切片（110 s 切 + 1 s 重叠 + 时间戳拼接） |
| 语种 | 自动识别（实测日语音频直出日语文本） |

> 对照（仅记录，不采用）：本地 sherpa-onnx + SenseVoice-int8 跑同一段 28.61 s → 2,734 ms、30 个时间戳，但文本质量明显低于云端（int8 量化 + 无 VAD 分段）。

## 10. 运维侧实测

| 项 | 实测 |
|---|---|
| 进程存活 | 从 **SSH 会话**里 `Start-Process` 起的 node **会随会话结束被杀**；改用 `Invoke-CimMethod Win32_Process Create` 才脱离会话存活 |
| ⇒ 正式部署 | sidecar **必须由计划任务托管**（照 `ZipperAIQQ-DouyinSidecar` 体例） |
| 输出管道 | 原生 exe 的输出**用管道接 `Select-Object` 会挂住**（npm、ffmpeg 都踩过）→ 一律重定向到文件再读 |
| 服务器 .NET | **没有 dotnet 运行时**（本地开发机有 10.0.403）→ 任何 .NET 侧组件只能以 self-contained 方式部署 |
| Defender | 常驻占用明显（CPU 累计 2,575 s）；`@ffmpeg-installer` 的 exe 一跑即挂，疑似被拦（未确证） |

## 15. 出站 HTTP API 的签名逆向（2026-11-21）

> 目标：让「发消息」走 `POST imapi.douyin.com/v1/message/send`，彻底摆脱 DOM。
> 结论：**签名解出来了，但请求仍被安全层拦住**；下面把每条尝试都留档，避免以后重走。

### 15.1 已是事实

| 项 | 结论 |
|---|---|
| 发送端点 | `POST https://imapi.douyin.com/v1/message/send`，`application/x-protobuf` |
| 请求体 | `im_proto.Request{ cmd=100, sequence_id, sdk_version="0.1.8", build_number="0d50935:feat/pc-im-group", body.send_message_body{…} }` |
| 鉴权 | 靠 cookie；无自定义 token 头 |
| 反爬（URL 级） | `verifyFp` / `fp`（cookie `s_v_web_id`）、`msToken`，以及 `X-Bogus` |
| 反爬（请求级） | `bd-ticket-guard-client-data` / `-version` / `-web-version` / `-web-sign-type` / `-ree-public-key`、`x-tt-session-dtrait` |

### 15.2 每条尝试与结果

| # | 尝试 | 结果 |
|---|---|---|
| 1 | 抓包原样重放（同 body + 原头） | ✅ 200 |
| 2 | 同头 + **换新 body** | ❌ 403 → 浏览器报 `Failed to fetch` |
| 3 | 自己拼 body + 只带 `content-type` | ❌ 被 secsdk 的 `blockFetch` 拦（栈指向 `runtime_bundler` / `sdk-glue`） |
| 4 | 用 `XMLHttpRequest`（页面已给 `send` 打补丁） | ❌ status 0 |
| 5 | `byted_acrawler.frontierSign(url)` 取 `X-Bogus` | ⚠️ 拿到值，但仍 403 |
| 6 | 蹭 `window.__zipperHeaders`/`performance` 里的历史头 | ❌ 仍被拒（签名与请求体绑定） |
| 7 | 直接调 `SDKRuntime.global.webSignUrl / webSignBody` | ⚠️ 返回 `{url, headers:{}}` —— **空头**（需 strategy 上下文） |
| 8 | 合成 context 调 `executeFetchRequest`（`webSign`/`csrfWebToken`） | ❌ 分别报 `undefined.apply` / `addHeader is not a function`（context 必须是 SDK 内部类） |
| 9 | 注入 webpack chunk 拿模块表找 IM SDK | ❌ 只能拿到 `webpackChunkdouyin_web` / `…UcSecureConsumerSDK`，`req.c/m` 不可枚举 |
| 10 | 用页面自己的 `frontier-im` WS 发 `SendMessage` 帧（service=5/method=1） | ⚠️ 帧发得出去，**无回执**；网页端发送不走 WS（WS 只推入站） |
| 11 | **`window.ucSecureConsumerSDK.sign({url, method, body})`** | ✅ **真拿到了 5 个 `bd-ticket-guard-*` 头**（`state=ready`，`cryptoUsage=system`） |
| 12 | 签名头 + `fetch` / `XHR` 发新 body（含补 `x-tt-session-dtrait`、`msToken`、`X-Bogus`） | ❌ 仍 `Failed to fetch` / status 0 |

### 15.3 打通（2026-11-21 凌晨，`status_code=0 OK` 且消息真的到达）

关键三个发现，缺一不可：

| # | 发现 | 说明 |
|---|---|---|
| 1 | **在 Node 侧发**（Playwright `context.request`） | 页面内 `fetch`/`XHR` 被 secsdk 拦成 `Failed to fetch`；`context.request` 与浏览器共享 cookie 却不受页面 CORS/`blockFetch` 约束 → 直接 200 |
| 2 | **签名用页面里的 `window.ucSecureConsumerSDK.sign()`** | 返回 `bd-ticket-guard-*` 五件套（`state=ready`、`cryptoUsage=system`）；照抄抓包头不行，必须让它现签 |
| 3 | **会话凭证要 seed** | 发送家族的 `headers` 必须有 `identity_security_token`（约 207 B 的 JSON）+ `identity_security_device_id`；页面**轮询**接口的请求体里没有它们 → 照抄会报 `invalid access param` |

另外两个字段上的硬要求（都是逐字段 diff 抓包比出来的）：

- `access = "web_sdk"`、`biz = "douyin_web"` —— 缺了直接 `invalid access param`
- `inbox_type = 0`（发送家族） vs `1`（轮询家族）
- **不要带 `channel`** —— 发送请求里没有这个字段

落地实现（`douyin-web-sidecar/src/send-api.ts`）：

```
旁听页面自己的 imapi 请求体  →  取 headers / 客户端标识当「会话模板」
+ seed 文件（identity_security_*，来自一次真实发送）
→ buildSendPayload（只换 body.send_message_body 与 sequence_id）
→ page.evaluate(ucSecureConsumerSDK.sign) 拿 ticket-guard 头
→ context.request.post() 发送
→ 解 im_proto.Response，status_code=0 才算成功（否则原样回填 errorDesc）
```

真实产出：`{ ok: true, statusCode: 0, logId: "…" }`，且重载私信页后能看到刚发的那条。

### 15.4 图片发送：纯 API 打通（2026-11-22，`skey=64 字符`）

图片是最难的一环，卡了很久，最后是**照旧基座 `douyin-im` 的 `services/im/upload.js` 逐段对齐**才通。
三处差异，每一处都能让请求失败：

| # | 正确做法（旧基座） | 我们之前的错法 | 症状 |
|---|---|---|---|
| 1 | `s` = **随机 11 位**（`a-z0-9`），参与签名 | 写死抓包里的常量 `sfhwtpaupd` | `SignatureDoesNotMatch` |
| 2 | 只签 `x-amz-date` / `x-amz-security-token`（POST 再加 `x-amz-content-sha256`），**不签 `host`** | 把 `host` 也放进 SignedHeaders | 同上 |
| 3 | Commit 带 `Functions:[{name:"Encryption", input:{Config:{copies:"cipher_v2"}, PolicyParams:{"policy-set":"check,thumb,medium,large"}}}]` | 不带 | 平台只回 `Uri`，**不回 `SecretKey`** |

第 3 条是“消息发出去了但对方看不到”的真因：没有 `Encryption.SecretKey`（即 content 里的
`resource_url.skey`），消息照样 `status_code=0`，但接收端渲染不出图。

完整链路（`send-api` + `image-upload`）：

```
① GET  /aweme/v1/web/im/upload/config/v2         → STS（**必须页面同源 fetch**，否则被 WAF 回 "blocked"）
② GET  vod.bytedanceapi.com?Action=ApplyUploadInner&…&s=<随机11位>       （SigV4）
③ POST https://<host>/upload/v1/<StoreUri>       Authorization / Content-CRC32 / X-Storage-U / UploadHeader
④ POST vod.bytedanceapi.com?Action=CommitUploadInner  {SessionKey, Functions:[Encryption…]}
     → Result.Results[0].Encryption{Uri, SecretKey, SourceMd5, Extra{img_size,img_width,img_height}}
⑤ POST imapi /v1/message/send  message_type=27
     content = {resource_url:{oid,skey,data_size,md5}, md5, cover_width, cover_height,
                check_pics:[], from_gallery:1, aweType:2702}
```

真机验收：

```
[info] 图片上传完成：oid=tos-cn-o-00061/baf8078b0… skey=64 字符
[info] 发送结果: {"ok":true,"statusCode":0,"logId":"20261122004844A70E06999D80AD2EC257"}
```

### 15.6 入站：事件优先，DOM 只是最后一层

| 层 | 机制 | 说明 |
|---|---|---|
| **L1（主路）** | 旁听页面 WS（`frontier-im`）的帧事件 | 无轮询、零延迟 |

保活（对齐旧基座的长连语义）：启动/重建后**自动打开最近会话**（列表延迟时重试 6 次），

### 15.7 登录态保活（血泪）

Chromium 的 Cookies 库在**进程被硬杀 / context 重建**时经常来不及落盘：真机上出现过
「重启后回到扫码弹窗 → 入站 WS 从不建立 → 22 小时一条消息没收到」。
现在 `DouyinBrowser.start()` 会先 `await restoreStorageState()`，把
`data/storage-state.json` 的 cookie 灌回 context（谁新谁赢）。
