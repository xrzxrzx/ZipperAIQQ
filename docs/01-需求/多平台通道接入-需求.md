## 决策一：邮件走进程内模块（`IMessageSource`）

### 依据

- 邮件**只收不发**（ZipperMessageGateway 需求明确：不做发送、回复、转发），`IMessageChannel.SendAsync` 对邮件是空语义
- .NET 有成熟 IMAP 库（MailKit），**没有跨语言 / 跨进程的必要**
- 进程内可直接复用 Core（配置/日志/事件总线）、Storage（SQLite）、Agent（`IChatClient` 做摘要）
- **目的**：邮件不是给客户端看的列表，而是**汇总 → 总结 → 转发给 QQ 里设置的主人**（见决策九）

### 做什么

1. 新增 `IMessageSource`：只有 `Platform` + `ReceiveAsync`（入站），不含发送
2. 新增 `MailSource`：IMAP 多账号、断线重连、**错误隔离**（一个账号失败不拖累其他账号）
3. 邮件会话模型独立于 `ChatType.Private/Group`（邮件是"通知流"，不是对话流）——用独立 `IncomingMail` 事件，**不新增 `ChatType`**
4. **输出路径**：摘要 +「是否需要处理」汇总后，**转发给 QQ 里设置的主人**（不进入对话回复链路）

### 不做什么

- ❌ 不实现 `IMessageChannel`（避免 `SendAsync` 空转、避免污染接缝 B）
- ❌ 不做邮件发送 / 回复 / 转发
- ❌ 不做附件解析（与邮件需求 P2 对齐）
- ❌ 邮件**不进**「人员与名单」的平台下拉框（只收不回，没有"谁能指挥它"的概念）

### 验收标准

- 三类邮箱（**QQ / 163 / Outlook**）各接 1 个账号，`ReceiveAsync` 能持续产出邮件事件
- 人为让 1 个账号凭据失效 → 其余账号继续收信，且日志/界面显示失效原因
- 摘要失败时**不丢信**（邮件仍可读，显示失败原因）
- 汇总/摘要能**转发到主人 QQ 私聊**（≤5 分钟）

### 风险

- IMAP 多账号连接管理（IDLE / 轮询、重连退避）是主要复杂度
- 邮件凭据敏感度高于 QQ 号（REQ-08 要求日志 0 命中）→ Core 日志脱敏必须覆盖
- **Gmail 本期不做**（从家用网络 IMAP 不可达 + 认证复杂）；范围仅 QQ / 163 / Outlook

## 决策二：抖音新建 `/ws/channel` 端点

### 依据

- `douyin-im` 是 Node 22.5+ 库（ESM + `node:sqlite`），**.NET 无法直接调用，必须跨进程 sidecar**
- 现有 `/ws/ext` 是「外部应用收发 QQ 消息」的**旁路**，**没有入站注入方向**（不能把外部消息变成 AI 的输入）
- 三个单平台硬绑证据：
  - `ZipperAIQQ.Server/External/ExternalCommandHandler.cs:111` —— `SessionRefParser.TryParse(sessionId, _channel.Platform, ...)` 只认单平台
  - `ZipperAIQQ.Server/External/ExternalCommandHandler.cs:131` —— 直接调单例 `_channel.SendAsync`
  - `ZipperAIQQ.Server/External/ExternalWsHub.cs:63` —— 构造注入单例 `IMessageChannel`，取它的 `Capabilities` / `SelfId`

### 做什么

1. 新建 `WS /ws/channel` 端点，**与 `/ws/ext` 分语义**（旁路 vs 通道接入），不混用
2. 帧形状复用 `ExternalProtocol` 的 `{type, time, data}`，新增方向：
   - `inbound`：sidecar → Server（平台消息注入）
   - `outbound`：Server → sidecar（发送指令）
   - `hello` / `ack` 复用现有语义
3. 鉴权复用 `HttpAccessPolicy`（Bearer token，loopback 免验）+ 每块 token（与 `ExternalReverseServer` 同口径）
4. 入站幂等：按平台 `messageId` 去重（断线重连不重复处理）
5. **候选查询**：`query.contacts` / `query.groups` 两个方向，供客户端「人员与名单」按平台选人（见决策四）

### 协议草案（方向，非最终）

```jsonc
// sidecar → Server：入站消息
{"type":"inbound","data":{
  "platform":"douyin",
  "session":"douyin:g123",
  "messageId":"...",
  "sender":{"userId":"...","nickname":"..."},
  "segments":[{"type":"text","text":"..."}],
  "time":0
}}

// Server → sidecar：出站发送
{"type":"outbound","data":{
  "session":"douyin:g123",
  "segments":[{"type":"text","text":"..."}],
  "requestId":"..."
}}
```

### 不做什么

- ❌ 不改 `NapCatChannel` 现有实现
- ❌ 不让 `/ws/ext` 承担通道语义（旁路继续可用）
- ❌ 不把抖音塞进 OneBot 11 协议（语义不符）

### 验收标准

- sidecar 连上 `/ws/channel` 后，抖音私聊/群消息能进入 AI 处理链路并产生回复
- 断线重连后不重复处理（按 `messageId` 幂等）
- 出站按 `session` 前缀路由到正确通道，不串平台

### 风险

- `douyin-im` 大量接口标注「未真实账号验收」（登录分支、follow、表情等）
- 登录需人机交互（扫码 / 短信 / 滑块），远程宿主需 `verification.openUrl`
- **7×24 运行可能因票据过期掉线**：`account.markActive()` 依赖真实用户活动，被动收消息不算
- 逆向协议违反平台 ToS，封号风险自担

## 决策三：外部 WS 升级为通用通道协议

### 现状问题

`/ws/ext` 现在是「旁路」（看 QQ 消息 + 代发 QQ 消息），带三个单平台假设（见决策二证据）。

### 目标形态

```
CompositeMessageChannel
  ├─ NapCatChannel（进程内，现状不动）
  ├─ MailSource（进程内，决策一）
  └─ WsChannelSource（进程外，抖音 sidecar 连入）
        ↑
  /ws/channel（复用 ExternalProtocol 帧 + 传输层）
```

### 做什么

1. `IMessageSource`：入站抽象（`Platform` + `ReceiveAsync`）
2. `CompositeMessageChannel`：合并多来源入站；出站按 `Platform` 路由
3. `MessageRouter`：从消费单通道改为消费复合通道（当前是单循环 `_channel.ReceiveAsync`）
4. `SelfId` / `ChannelCapabilities` 按平台（当前 `ServerOptions.SelfId` 是单值）
5. `/ws/channel` 端点与帧协议（决策二）

### 不做什么

- ❌ 不改 NapCat 现有实现
- ❌ 不破坏 `/ws/ext` 现有语义（旁路继续可用）

### 验收标准

- QQ + 邮件 + 抖音同时在线时，各平台上下文不串（`ChatRef.SessionId` 已带平台前缀，数据层已就绪）
- 出站消息按 `Platform` 路由，不串平台
- 新增一个平台 = 新增一个 `IMessageSource` 实现 + 一行注册（对齐 FR-1.2）

### 风险

- 单例 → 多实例涉及 `ServiceRegistration` 多处改动：`ThrottledMessageChannel`、`IContactDirectory`、`OwnerScopeResolver`、`ISessionNameResolver` 都还是单平台假设
- 改动面比前两个决策大，**建议单独一批、独立验证**

## 决策四：配置平台化（人员与名单）

### 依据

- 现在「人员与名单」三处写死 QQ：`AccessViewModel.cs:106` 拼 `qq:p`、`AccessActions.cs:142` 拼 `qq:g`、`GetAccessAction` 注入单例 `IContactDirectory`
- 抖音接入后，主人 / 管理员 / 名单必须能**按平台分别配置**

### 做什么

1. **人员（owner / admins）按平台存**：`access.{platform}.owner` / `access.{platform}.admins`
2. **名单（white / black）按平台存**（用户拍板）：`access.{platform}.whitelist` / `access.{platform}.blacklist`
3. 客户端「人员与名单」页顶部加**平台下拉框**（QQ / 抖音），切换即重新加载
4. `getAccess` / `setOwner` / `setAccess` 增加 `platform` 参数（缺省 `qq`，兼容旧客户端）
5. 角色解析按平台：`IRoleResolver.Resolve(userId, platform)`；`OwnerScopeResolver` 按平台查询好友 / 群
6. 候选人来源按平台：`IContactDirectory` 注册表（QQ → NapCat，抖音 → sidecar 的 `query.contacts` / `query.groups`）

### 不做什么

- ❌ 邮件**不进人员下拉框**（只收不回，没有"谁能指挥它"的概念）
- ❌ 不做跨平台"同一个人"的关联

### 验收标准

- QQ 与抖音各自配置主人 / 管理员不互相覆盖
- 切换平台后名单只显示该平台的会话条目
- 旧配置（无平台）自动视为 `qq`，不丢数据

### 风险

- 旧键惰性迁移（参考现有 `filterMode` / `filterEntries` 做法）
- `IContactDirectory` 从单例改成按平台取，影响面较大

## 决策五：工具平台适配

### 依据

- 工具有三类：**通用**（文件、搜索、记忆）、**需适配**（发消息、联系人查询）、**平台专用**（戳一戳、表情包、语音转写）
- 现在工具注册不区分平台，抖音接入后会出现"给抖音发戳一戳"这种事

### 做什么

1. 工具声明**平台要求 / 能力要求**（新增元数据）
2. 按当前会话平台动态过滤工具列表：
   - 通用工具 → 所有平台可见
   - 需适配工具 → 走统一抽象（`SendMessageTool` 不感知平台）
   - 平台专用工具 → 只对对应平台可见（QQ：戳一戳 / 表情 / 语音；抖音：抖音专用 API）
3. 新增**抖音专用 API 工具**，注册进 `IToolRegistry`，并出现在客户端「工具配置」
4. 客户端工具配置页**按平台分组**，标出平台专用工具

### 不做什么

- ❌ 不在工具内部 `if (platform == ...)` 分支（用能力声明 + 注册表过滤）
- ❌ 不为抖音重复实现通用工具

### 验收标准

- 抖音会话里 `list_tools` 不出现 QQ 专用工具
- QQ 会话里不出现抖音专用工具
- 通用工具两个平台都能用
- 客户端工具配置能看到平台分组

### 风险

- 工具能力声明是新增元数据，现有工具要逐个标注
- `GuardedAIFunction` 的权限门禁保持不变

## 决策六：通知类型平台口径

### 依据

- 现有 `NoticeType` 是 OneBot / QQ 语义（戳一戳、入群、群文件、群精华…）
- 抖音的通知完全不同（好友申请、入群申请、成员变化、会话同步）

### 做什么

1. `NoticeType` 增加**平台归属**，或按平台拆分枚举（`QqNoticeType` / `DouyinNoticeType`）
2. 「运行与行为」页的通知开关**按平台分组**（QQ 口径 / 抖音口径）
3. `getBehavior` 返回的 `notices` 带 `platform` 字段；`setBehavior` 按平台写

### 不做什么

- ❌ 不把抖音通知硬塞进 QQ 枚举（语义不符）
- ❌ 不删现有 QQ 通知配置

### 验收标准

- 行为页能分别看到 QQ 与抖音的通知类型
- 关闭某平台通知不影响另一平台
- 旧配置（无平台）视为 QQ

### 风险

- `NoticeType` 参与设置键（`notice.reply:{type}`），改键要兼容旧值

## 决策七：第三方平台接入配置页

### 依据

- 抖音 / 邮件的配置现在没有落脚点（邮件靠环境变量，抖音还没有）
- 用户要求：单独配置页，分页「邮件 / 抖音」；邮件配置**参考 WS 通道（外部接口）的配置逻辑和 UI**（数据块）

### 做什么

1. 新增客户端页面「第三方平台接入」，页面内 `Pivot` 分页：**邮件** / **抖音**（以后加平台加 Tab）
2. **邮件页**：参考 `ExternalPage` 的数据块（卡片网格）
   - 每个邮箱账号一张卡片（地址 / IMAP 主机 / 启用开关 / 状态）
   - 新建 / 编辑 / 删除 / 保存（与 `ExternalPage` 同交互）
   - 凭据只显示掩码，编辑时重填
3. **抖音页**：sidecar 地址、token、登录状态、白名单（同样数据块）
4. 服务端提供对应读写 action

### 不做什么

- ❌ 不做平台插件化动态加载（先把两个平台做稳）

### 验收标准

- 两个 Tab 各自能增删改并保存生效
- 邮件凭据不明文回显
- 抖音页能看到 sidecar 连接状态

### 风险

- 新页面要接导航、DI、配置服务
- 邮件与抖音配置结构差异大，数据块模板要抽象

## 决策八：`/help` 改发图片

### 依据

- 现在 `HelpCommand` 返回纯文本，QQ 里对齐会错位（与 `/status` 当初的问题相同）
- `StatusCommand` 已实现 `IImageCommand`，用 `StatusImageRenderer` 渲染 PNG

### 做什么

1. `HelpCommand` 实现 `IImageCommand`，返回 `(Text, byte[]? Png)`
2. 用 `StatusImageRenderer`（或抽通用表格渲染器）画命令列表：命令名 / 说明 / 最低角色
3. 保留 `ExecuteAsync` 文本版作为兜底
4. 按平台过滤命令（与决策五联动：抖音会话不显示 QQ 专用命令）

### 不做什么

- ❌ 不改 `IImageCommand` 接口本身（已是"文本 + 图片"的通用形状）

### 验收标准

- `/help` 收到的是图片（文本为空或仅说明）
- 图片内容与当前角色可见命令一致
- 渲染失败时回落文本

### 风险

- 字体缺失时渲染会失败 → 必须有文本兜底
- 命令列表长了图片会很高（需限制或分列）

## 决策九：邮件输出 = 转发给 QQ 主人

### 依据

- 用户明确：邮件只接收不回复，**汇总再总结转发给 QQ 里设置的主人**
- 与 ZipperMessageGateway 需求（"推桌面端与手机端"）的差异：本项目改为**转发到 QQ 主人**

### 做什么

1. 邮件到达 → 落库 → 摘要（≤3 句 + 是否需要处理）
2. 汇总（可配：单封即转 / 每 N 分钟合并 / 每日汇总）
3. 通过 `IMessageChannel` 发给**当前平台的主人**（主人配置见决策四）
4. 转发失败要重试 + 可见错误（不静默丢）

### 不做什么

- ❌ 不回复邮件
- ❌ 不在 QQ 里暴露完整邮件正文（只发摘要 + 来源）

### 验收标准

- 新邮件到达后，主人 QQ 私聊收到汇总
- 主人未配置时明确提示（不静默丢弃）
- 转发失败可在客户端看到原因

### 风险

- 与决策四耦合（主人按平台）
- 汇总频率要可配，避免刷屏
