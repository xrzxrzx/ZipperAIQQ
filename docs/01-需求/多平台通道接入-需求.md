## 0. 一句话总览

三个决策围绕同一件事：**让「平台通道」可扩展**——邮件走进程内、抖音走进程外 WS，两者汇入同一条「通道接入」链路。

## 决策一：邮件走进程内模块（`IMessageSource`）

### 依据

- 邮件**只收不发**（ZipperMessageGateway 需求明确：不做发送、回复、转发），`IMessageChannel.SendAsync` 对邮件是空语义
- .NET 有成熟 IMAP 库（MailKit），**没有跨语言 / 跨进程的必要**
- 进程内可直接复用 Core（配置/日志/事件总线）、Storage（SQLite）、Agent（`IChatClient` 做摘要）

### 做什么

1. 新增 `IMessageSource`：只有 `Platform` + `ReceiveAsync`（入站），不含发送
2. 新增 `MailSource`：IMAP 多账号、断线重连、**错误隔离**（一个账号失败不拖累其他账号）
3. 邮件会话模型独立于 `ChatType.Private/Group`（邮件是"通知流"，不是对话流）；若必须映射，新增 `ChatType.Mail` 或独立模型 —— **见待确认 Q1**

### 不做什么

- ❌ 不实现 `IMessageChannel`（避免 `SendAsync` 空转、避免污染接缝 B）
- ❌ 不做邮件发送 / 回复 / 转发
- ❌ 不做附件解析（与邮件需求 P2 对齐）

### 验收标准

- 四类邮箱（QQ/163/Gmail/Outlook）各接 1 个账号，`ReceiveAsync` 能持续产出邮件事件
- 人为让 1 个账号凭据失效 → 其余账号继续收信，且日志/界面显示失效原因
- 摘要失败时**不丢信**（邮件仍可读，显示失败原因）

### 风险

- IMAP 多账号连接管理（IDLE / 轮询、重连退避）是主要复杂度
- 邮件凭据敏感度高于 QQ 号（REQ-08 要求日志 0 命中）→ Core 日志脱敏必须覆盖
- Gmail 从家用网络 IMAP 不可达（ZipperMessageGateway 调研 §3.2）→ 需在需求冻结前定方案

## 决策二：抖音新建 `/ws/channel` 端点

### 依据

- `douyin-im` 是 Node 22.5+ 库（ESM + `node:sqlite`），**.NET 无法直接调用，必须跨进程 sidecar**
- 现有 `/ws/ext` 是「外部应用收发 QQ 消息」的**旁路**，**没有入站注入方向**（不能把外部消息变成 AI 的输入）
- 三个单平台硬绑证据：
  - `ZipperAIQQ.Server/External/ExternalCommandHandler.cs:111` —— `SessionRefParser.TryParse(sessionId, _channel.Platform, ...)` 只认单平台
  - `ZipperAIQQ.Server/External/ExternalCommandHandler.cs:131` —— 直接调单例 `_channel.SendAsync`
  - `ZipperAIQQ.Server/External/ExternalWsHub.cs:63` —— 构造注入单例 `IMessageChannel`，取它的 `Capabilities` / `SelfId`

### 做什么

1. 新建 `WS /ws/channel` 端点，**与 `/ws/ext` 分语义**（旁路 vs 通道接入），不混用
2. 帧形状复用 `ExternalProtocol` 的 `{type, time, data}`，新增方向：
   - `inbound`：sidecar → Server（平台消息注入）
   - `outbound`：Server → sidecar（发送指令）
   - `hello` / `ack` 复用现有语义
3. 鉴权复用 `HttpAccessPolicy`（Bearer token，loopback 免验）+ 每块 token（与 `ExternalReverseServer` 同口径）
4. 入站幂等：按平台 `messageId` 去重（断线重连不重复处理）

### 协议草案（方向，非最终）

```jsonc
// sidecar → Server：入站消息
{"type":"inbound","data":{
  "platform":"douyin",
  "session":"douyin:g123",
  "messageId":"...",
  "sender":{"userId":"...","nickname":"..."},
  "segments":[{"type":"text","text":"..."}],
  "time":0
}}

// Server → sidecar：出站发送
{"type":"outbound","data":{
  "session":"douyin:g123",
  "segments":[{"type":"text","text":"..."}],
  "requestId":"..."
}}
```

### 不做什么

- ❌ 不改 `NapCatChannel` 现有实现
- ❌ 不让 `/ws/ext` 承担通道语义（旁路继续可用）
- ❌ 不把抖音塞进 OneBot 11 协议（语义不符）

### 验收标准

- sidecar 连上 `/ws/channel` 后，抖音私聊/群消息能进入 AI 处理链路并产生回复
- 断线重连后不重复处理（按 `messageId` 幂等）
- 出站按 `session` 前缀路由到正确通道，不串平台

### 风险

- `douyin-im` 大量接口标注「未真实账号验收」（登录分支、follow、表情等）
- 登录需人机交互（扫码 / 短信 / 滑块），远程宿主需 `verification.openUrl`
- **7×24 运行可能因票据过期掉线**：`account.markActive()` 依赖真实用户活动，被动收消息不算
- 逆向协议违反平台 ToS，封号风险自担

## 决策三：外部 WS 升级为通用通道协议

### 现状问题

`/ws/ext` 现在是「旁路」（看 QQ 消息 + 代发 QQ 消息），带三个单平台假设（见决策二证据）。

### 目标形态

```
CompositeMessageChannel
  ├─ NapCatChannel（进程内，现状不动）
  ├─ MailSource（进程内，决策一）
  └─ WsChannelSource（进程外，抖音 sidecar 连入）
        ↑
  /ws/channel（复用 ExternalProtocol 帧 + 传输层）
```

### 做什么

1. `IMessageSource`：入站抽象（`Platform` + `ReceiveAsync`）
2. `CompositeMessageChannel`：合并多来源入站；出站按 `Platform` 路由
3. `MessageRouter`：从消费单通道改为消费复合通道（当前是单循环 `_channel.ReceiveAsync`）
4. `SelfId` / `ChannelCapabilities` 按平台（当前 `ServerOptions.SelfId` 是单值）
5. `/ws/channel` 端点与帧协议（决策二）

### 不做什么

- ❌ 不改 NapCat 现有实现
- ❌ 不破坏 `/ws/ext` 现有语义（旁路继续可用）

### 验收标准

- QQ + 邮件 + 抖音同时在线时，各平台上下文不串（`ChatRef.SessionId` 已带平台前缀，数据层已就绪）
- 出站消息按 `Platform` 路由，不串平台
- 新增一个平台 = 新增一个 `IMessageSource` 实现 + 一行注册（对齐 FR-1.2）

### 风险

- 单例 → 多实例涉及 `ServiceRegistration` 多处改动：`ThrottledMessageChannel`、`IContactDirectory`、`OwnerScopeResolver`、`ISessionNameResolver` 都还是单平台假设
- 改动面比前两个决策大，**建议单独一批、独立验证**

## 风险总表

| 风险 | 影响 | 缓解 |
|---|---|---|
| `douyin-im` 未真实账号验收 | 抖音接入可能跑不通 | 先小号 POC 验证收发与掉线恢复 |
| 票据过期掉线 | 7×24 不稳定 | 监控 + 自动重登 + 心跳 |
| 单例改多实例 | 改动面大、易回归 | 单独批次 + 独立验证（审查者 ≠ 作者） |
| 邮件凭据泄露 | 安全问题 | 日志脱敏 + 加密落库（对齐现有 LLM key 做法） |
| 邮件与对话语义混淆 | 数据模型污染 | Q1 先定模型边界 |
