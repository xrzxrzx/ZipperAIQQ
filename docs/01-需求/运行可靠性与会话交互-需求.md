## 2. 需求条目

### R-01 功能异常主动反馈（多通道降级上报）

**来源（原话）**

「功能异常时需要能主动反馈给主人。默认走 QQ 通道。QQ 走不通时，需要依次尝试其他平台通道。只有所有通道都走不通时才作罢。」

**现状**

- 已有「主人反馈」能力（`ZipperAIQQ.Server/Feedback/`），但它是**业务事件**（通知/撤回等）的转发，不是「系统自身异常」的上报。
- 异常目前只有日志一条出口：例如定时任务发送失败直接 `SendAsync` 抛出（`ZipperAIQQ.Server/Scheduler/SchedulePoller.cs:100`），失败既不通知创建者也不通知主人。
- 没有「多通道依次尝试」的发送器：调度器持有的是**单例** `IMessageChannel`，一条消息只会走一个平台。

**期望形态**

1. 定义**系统异常事件**（通道断开、定时失败、LLM 连续失败、内存/耗时越阈）为**一类可上报事件**，与业务通知同构；
2. 上报默认发给**主人私聊（QQ）**，可按配置改为其他会话；
3. 发送走**通道降级链**：QQ → 下一平台 → …，每次失败记原因，全挂则落库待补发；
4. 有**抑制/合并**：同一异常在窗口内只报一次，避免断网时把每个失败都发一遍（那会把通道打得更死）。

**验收口径（草案）**

- 人为断掉 QQ 通道 → 5 分钟内必须出现一次**通过其他通道**送达的异常上报（这一条同时验证「自己报自己挂了」这个自指场景能走通）；
- 所有通道都不可用时，上报落库；通道恢复后补发一次，不重复刷屏；
- 同一异常（同类型 + 同目标）在 N 分钟内只上报一次，N 可配；
- 上报内容不含机密（沿用日志脱敏口径）。

**待拍板**

| # | 选项 | 代价 / 收益 |
|---|---|---|
| 1 | 降级链**固定顺序**（QQ → 抖音 → 邮件…） | 简单可预测；但顺序里的第一个挂了每次都要等超时 |
| 2 | 降级链**按最近一次可用性**动态排序 | 更快；要多维护一份健康度状态，出错时更难解释 |
| 3 | 邮件当兜底 | 收益：QQ/抖音全挂时还有独立通路；代价：目前邮件**只收不发**（`多平台通道接入-需求.md` 决策一明确不做发送），要做就得先立「邮件发送」需求 |

**影响面**：通道层（多通道发送能力）、Server 通知/反馈模块、接缝 B（不得依赖平台类型）。

### R-02 通道断线自愈

**来源**：同 `问题记录-04` Q4-01。

**期望形态**

1. 通道具备「断开 → 退避重连 → 恢复」的闭环，**无需人工重启**；
2. 断线期间出站消息**不丢队头、不重复**；
3. 断线/重连状态**可观测**（`/status` 或审计页 + 指标），并可作为 R-01 的异常源。

**验收口径（草案）**

- 拔网线 30 秒再插回：≤ 60 秒内自动恢复收发，无需重启；
- 连续失败退避有上限（例如 30 秒封顶），且不会因退避把恢复拖到几分钟；
- 重连成功后日志有一条「断开 X 秒」记录；
- 断线期间入站消息按平台能力处理（要么缓存补处理，要么明确丢弃并计数）——**这一点必须二选一并写死**。

**待拍板**

| # | 选项 | 代价 / 收益 |
|---|---|---|
| 1 | 重连放在 `NapCatChannel` 内部 | 通道自洽；但每个平台实现都要写一遍 |
| 2 | Server 侧加 Supervisor（通道统一被守护） | 一处管所有平台；多一层间接，调试多看一层 |
| 3 | 是否连 NapCat 进程一起拉起 | 收益：NapCat 崩了也能救；代价：跨进程进程管理，权限与路径问题多 |

**影响面**：通道层 / 组合根；接缝 B。与 `问题记录-04` Q4-01 同一处代码。

### R-03 定时任务执行结果回灌 Agent

**来源（原话）**

「期望逻辑是：到点后执行任务，执行完成后将反馈丢给目标会话的 Agent，再由 Agent 判断发送什么。当前定时任务的逻辑需要优化。」

**现状**

- 到点后**直接发送**，完全绕过 Agent：`SchedulePoller.cs:76 → :90 → :100 _channel.SendAsync(...)`；
- 成功才写库（`:105` `AppendOutgoingAsync`），**失败没有任何回执**；
- 创建时把会话写死（`ZipperAIQQ.Agent/Tools/ScheduleTools.cs:84-94`），`target` 只能改目标，改不了「由谁来说」。

**期望形态**

到点 → 执行任务（产出「结果」或「失败原因」）→ 作为一条**内部事件**投给目标会话的 Agent → Agent 决定发什么、怎么发、要不要发。

**必须一起定清的四个问题（拍板项）**

| # | 问题 | 选项 / 代价 |
|---|---|---|
| 1 | Agent 可不可以**决定不发**？ | 可以：更像人，但「定了时却没动静」会显得任务丢了，需要审计兜底；不可以：到点必发一条，但那就等于回到现状 |
| 2 | 每次定时都跑一次 LLM 的**成本**能否接受？ | 一天几十个任务 = 几十次调用；可加「轻量模式」（模板化发送 + 只在失败时叫 Agent） |
| 3 | **循环风险**：Agent 在执行任务时又创建定时任务 | 需要「任务执行中」标记与创建抑制，否则可能自我繁殖 |
| 4 | 与用户消息的**先后**：目标会话正有对话在跑，定时结果排队还是插入？ | 排队简单；插入与 R-04 共用中断机制 |

**验收口径（草案）**

- 任务到点 → Agent 收到结果（成功/失败/内容），可观测到这次「决策」；
- 发送失败 → Agent 能选择通知创建者（配合 R-01）；
- 同一任务不得重复执行（配合 `问题记录-04` Q4-06 的幂等）；
- 不发送时必须留审计（谁决定不发、为什么）。

**影响面**：`ZipperAIQQ.Server/Scheduler`、Agent 会话入口；**FR-14 的 14.4 需要改写**（现写的是「任务完成后可向指定会话发送结果」，与新逻辑不再等价）。

### R-04 思考中插入新消息（引导，而非排队）

**来源（原话）**

「AI 正在思考时又有消息到来……期望：可以把新消息插入到思考中做引导。类似各种 Agent 工具中的插入消息机制。」

**现状**

- 方案已讨论、**未拍板**：`docs/03-设计/思考中新消息处理策略.md`（三个方案 A 分层 / B 并行预判断 / C 组合；JEV 评估置信度 0.31，未据此决策）；
- 当前行为：新消息进队列等这一轮结束再合并处理（同文档 §一）。
- ⚠️ **参考实现（2026-11-03 新证据）**：Pi 的 `agent.steer()` / `agent.followUp()` 把这个问题从「要不要打断」改写成「投哪个队列」——`steer` 在当前 assistant 的工具调用**全部完成后**注入、下一轮回应；`followUp` 等这轮**本会结束**时再投递；`steeringMode` / `followUpMode` 各有 `one-at-a-time`（默认）/ `all`。详见 `docs/06-调研/Pi-Agent-可替代性调研.md`。**建议据此重写本需求的方案部分**，而不是在 A/B/C 里再选一次。

**期望形态**

新消息在**思考进行中**可被「插入」当前轮作为引导，同时用「连续中断上限」防止刷屏时永远跑不完一轮。

**待拍板（直接沿用既有文档，不在这里重复设计）**

- [ ] 选 A / B / C / 暂不改（该文档 §二）
- [ ] 私聊是否直接中断（不判断）
- [ ] 连续中断上限（建议 2）
- [ ] 是否记录 `reply.interrupted` 指标

**验收口径（草案）**

- 插入后**不产生第二次独立回答**（这是 `问题记录-05` Q5-03「抖音响应两次」的同一处判据）；
- 已发生的工具副作用不回滚，且状态标志可靠（该文档 §五「状态回滚」）；

**影响面**：Agent 会话队列 + `CancellationToken` 传播；与 R-10 同源。

### R-05 名单模型重设计（显式模式 + 单份名单）

**来源（原话）**

「考虑把两个名单合并。用一个开关决定是白名单还是黑名单模式。当前歧义太严重，需要重新设计。」

**现状**

- 现行是**两份名单并存 + 条数反推模式**：`ZipperAIQQ.Channel/Filtering/ChatFilter.cs:155-175`（黑名单优先 → 主人放行 → 白名单非空即 deny-by-default）；`ZipperAIQQ.Server/Api/Handlers/AccessActions.cs:241-247`（白名单有内容即当 White 模式）。
- 「两份并存 + 互斥」本身是 **`问题记录-01` #20 拍板过的结论**，2026-10-29 的 D75 又定了「黑名单优先于主人放行」。
- 所以本需求**不是修 bug，而是要替换一个已定过的设计** —— 这条必须由用户明确拍板，不能顺手改。

**期望形态（用户设想）**

一份名单 + 一个**显式模式开关**（白 / 黑）；空名单语义唯一且写死在 UI 上；主人放行规则保留（黑名单优先）。

**待拍板**

| # | 问题 | 选项 / 代价 |
|---|---|---|
| 1 | 保留「两份并存」还是收敛成「一份 + 模式」 | 收敛：心智简单，但**现有同时配了两份的用户需要迁移**（并集？强制二选一？） |
| 2 | 迁移策略 | 自动并集（可能放开原本该拦的会话）/ 让用户在升级后手动选一次（更安全，多一步操作） |
| 3 | 通配 `qq:p*`（`ChatFilter.cs:200-214`）是否保留 | 保留：抖音 sidecar 已有一批 `...p*` 条目；去掉：要改数据，且抖音「一条都收不到」会复发 |
| 4 | 「模式」如何影响入库（R-06） | 模式只决定「进不进模型」，入库另配（两件事分开）vs 模式一并决定（更简单，但用户失去「留档但不回复」的能力） |

**验收口径（草案）**

- 模式可读回：UI 显示的就是服务端判定用的那个值（不再由条数反推）；
- 白名单模式 + 空名单 = **全部不收**；黑名单模式 + 空名单 = **全部收**；两种文案在 UI 与 `/status` 里一致；
- 同一会话在两种模式下的接收结果可预测，不出现「关掉反而放开」；
- 黑名单优先于主人放行（D75 的结论不得被本次重设计推翻）。

**影响面**：`ChatFilter`、`AccessActions`（**对外契约**）、客户端人员与名单页、**FR-17 全面改写**。属「触碰权限/对外契约」——改动需用户抽查。

### R-06 消息入库可配置

**来源（原话）**

「加入黑名单后消息不会入库。想法是：消息入不入库也要可配置。具体实现方式还需讨论。」

**现状**

- 入库与放行**绑死**：过滤在通道层，未通过的消息**不落库、不进模型**（FR-17.3；`ChatFilter.cs:53-57` 注释明确写着这个安全理由）。

**期望形态**

把「是否入库」与「是否进模型 / 是否回复」拆成两个可配项，允许「留档但不回复」。

**待拍板**

| # | 问题 | 选项 / 代价 |
|---|---|---|
| 1 | 入库范围 | 全部入 / 仅被拦的入 / 仅白名单外入；范围越大，库越大 |
| 2 | 隐私口径 | FR-17.3 的安全理由（「非白名单内容根本不存在于本地」）会被推翻 —— **需要用户明确接受**，并在文档里写清楚 |
| 3 | 保留期 | 与日志一样按天清理？还是永久保留？清理策略要与日志归档共用还是各管一套 |

**验收口径（草案）**

- 同一会话：被拦 + 入库开启 → 库里有记录，**但不进模型、不回复**；
- 关闭入库 → 库里 0 条（可查证）；
- 列表（客户端）能看出「这条是留档，没回复」；
- 数据增长可观测（条数/体积），有清理或上限。

**影响面**：通道层过滤、存储、**FR-17.3 改写**（数据模型 + 隐私口径），需用户抽查。

### R-07 跨平台工具通用化

**来源（原话）**

「抖音目前无法做到跨平台调用工具，例如定时任务。这是工具通用性问题。」

**现状**

- 工具目录已经是平台无关的（`ZipperAIQQ.Agent/Tools/ToolCatalog.cs:37-39`，定时工具默认 `ToolPlatform.All`）；
- 卡口在**权限按平台分桶**：`ToolCapability.Schedule` 硬底线 `Admin`（`PermissionGate.cs:39`），而主人/管理员是 `RoleResolver` 按平台存的（`RoleResolver.cs:44-67`、`:127-141`）→ 抖音上没配管理员就永远调不到；
- 发送侧也是单平台：`SchedulePoller.cs:100` 单例 `_channel.SendAsync`。

**期望形态**

工具**只有「平台能力」这一种过滤理由**；权限走**跨平台的主人/管理员**；跨平台目标按 `session` 前缀路由到对应通道。

**待拍板**

| # | 问题 | 选项 / 代价 |
|---|---|---|
| 1 | 主人身份是否跨平台统一 | 统一：换平台仍是主人，管理能力不断；分离：每个平台一个主人，隔离好但要在每处重新配 |
| 2 | 抖音里能不能给 QQ 定定时任务 | 能：真正「跨平台」；不能：语义简单（定时只在发起平台生效），但用户会觉得残废 |
| 3 | 能力声明表是否要标「该平台不支持发送」 | 要：模型能提前知道并换路；不要：模型会尝试并失败，然后对用户说错话 |

**验收口径（草案）**

- 抖音会话里 `schedule_create` **可见且可用**（前提：配置了跨平台主人/管理员）；
- 目标为 `qq:g...` 时由 QQ 通道发出，不串平台；
- 权限被拒时模型拿到的是**可执行信息**（谁能做、能不能转交），不是一句「只有管理员能」；
- 权限拒绝进审计并可按平台统计。

**影响面**：`ToolCatalog`、`PermissionGate`、`RoleResolver`、`SchedulePoller`；接缝 B。

### R-09 记忆库互联（图状指向 + 注意力检索）

**来源（原话）**

「希望记忆模块做成类似 Obsidian 那样的记忆库形式，各文档/记忆点之间可以互相联系……给每个记忆点赋予一个 `n` 维向量，`n` 为全局确定。每个记忆点能够指向其他记忆点，也能被其他记忆点指向，指向数量不限。」「这套方案是否类似于进阶版向量库。希望引入注意力机制，类似 Transformer 架构中的注意力机制。」

**现状**

- 向量检索 + 摘要：`ZipperAIQQ.Agent/Memory/MemoryRetriever.cs`、`SummaryService.cs`；嵌入用进程内 ONNX：`ZipperAIQQ.Agent/Embedding/OnnxEmbeddingService.cs` + `BertTokenizer.cs`。
- **记忆点之间没有任何显式链接**（无「边」的概念）：检索是「query → top-k 相似」，不带图传播。
- 所以用户设想的形态**不是现状的微调，是新的一层结构**。

**这条要拆成「先定形态，再定机制」两步**

**第一步·形态（拍板项）**

| # | 问题 | 选项 / 代价 |
|---|---|---|
| 1 | 记忆点存储形态 | SQLite 表 + 边表（与现有栈一致，查询强）/ Markdown 文件 + `[[链接]]`（Obsidian 式，人可读可编辑，但要自己做索引）/ 图库（重，且引入新依赖） |
| 2 | `n` 从哪来 | 复用现成 embedding 维度（不改训练，最省）/ 另训（工作量大，收益不明） |
| 3 | 「指向」怎么产生 | 模型显式写（准，费 token）/ 相似度自动建边（免费，噪声大）/ 人工维护（最准，没人维护） |

**第二步·机制（待调研，不能直接拍）**

| # | 问题 | 说明 |
|---|---|---|
| 4 | 「注意力」到底指什么 | ① 检索打分（query-key 相似度 + 边权重传播，本质是 **RAG + 图扩散**，工程量可控）；② 真训练一个注意力层（要训练数据与算力，超出本项目当前形态）。**必须先说清选哪个**，否则「引入注意力」无法验收 |
| 5 | 与现有 top-k 的关系 | 图扩散是在 top-k 之后做（rerank + 邻居扩展），还是替换 top-k |
| 6 | 遗忘 / 衰减 | 记忆点要不要随时间降权、边要不要失效；不定的话库会单调膨胀 |

**验收口径（草案，待形态定稿后细化）**

- 能回答「与这个记忆点相关的还有哪些」并给出**链接理由**（边从哪来）；
- 一度邻居扩展后的检索结果，在固定测试集上**优于**纯 top-k（要有对照，不能只凭感觉）；
- 记忆库规模到 N 条时，检索延迟仍在预算内（给出数字）。

**风险**

这条极易变成「自己再造一个 RAG + 图数据库」。建议先做**最小闭环**（边表 + 一度邻居扩展 + 复用现有 embedding），验证「图确实带来更好召回」之后再谈注意力训练。

**影响面**：新模块；不触碰接缝 A/B（纯 Agent 侧能力）。

### R-10 轮次机制（思考中调工具 / 阻塞等待 / 超时收轮）

**来源（原话）**

「当前逻辑是：接受一次用户消息就是完整的一轮。如果这轮思维不停止，会怎样，需要讨论。」「理论上调用工具等操作都可以在思考中完成。这样做是否能够提高 AI 的注意力，需要讨论。如果没有消息，也可以阻塞等待。长时间没有消息后，可以结束这一轮。」

**现状**

- 一轮 = 一条用户消息 → `ChatAgent.RunAsync` 跑到结束（含工具循环）；轮结束后会话回到空闲；
- 没有「无消息时阻塞等待」：空闲即结束，没有挂起态；
- 可参考的粒度划分：Pi 用 `turn_start` / `turn_end`（一次 LLM 调用 + 工具执行 = 一个 turn）+ `agent_end`（整轮结束）+ `finishTurn` 返回 `{continue}` / `{end}` 决定「还要不要求下一轮」，并提供 `abort()` / `waitForIdle()`。见 `docs/06-调研/Pi-Agent-可替代性调研.md`；
- 因此「思维不停止会怎样」在现状里不存在（轮一定会终止），真正的问题变成：**要不要允许一轮跨越多条消息、跨越空闲期**。

**期望形态（待讨论，三种粒度）**

| 粒度 | 形态 | 代价 |
|---|---|---|
| 小 | 只在轮内允许「插入消息」（= R-04），轮仍然一条消息触发 | 改动小，与 R-04 重合 |
| 中 | 轮可以**阻塞等待**下一条消息（挂起 N 秒/分钟），期间收到即续轮 | 上下文/连接被长时间持有；会话队列要区分「挂起中」与「空闲」 |
| 大 | 轮是**长生命周期**的（工具调用都在「思考中」，空闲时等待，超时收轮） | 最接近用户描述；但需要明确「收轮产物」（总结？静默？审计？），否则会出现「无主的长会话」 |

**待拍板**

- [ ] 选哪个粒度（小 / 中 / 大）
- [ ] 阻塞上限（多少秒/分钟无消息就收轮），以及收轮时是否产出总结
- [ ] 「思考中调工具能否提高注意力」——这是**假设**，需要实验设计（同一批输入对比回答质量），不能凭感觉写进需求
- [ ] 与 R-04 的关系：中断（打断当前轮）与阻塞（等待下一条）是同一套状态机的两个方向，必须一起设计

**验收口径（草案）**

- 挂起期间不重复触发、不漏消息；同一会话不会出现两个并行轮；
- 超时收轮有审计与指标；收轮后状态明确（空闲 / 可被新消息唤醒）；
- 工具调用失败不终止轮（现状是否如此需核对，不在这里断言）。

**影响面**：`ChatAgent` 生命周期、会话队列、幂等；与 R-04 同源，建议同一份设计文档覆盖。

### R-12 额度使用上限（可选开关）+ 报警机制

**来源（原话，2026-11-05 追加）**

「服务端日志有大量报错，兜底机制不停调用 API 导致消耗了我大量额度！……这个之后要做一个额度使用上限（可选开不开启）和报警机制。」

**背景（一句话）**

11-05 那条 QQ 机器人 key 单日烧掉 ¥28.84。根因已查清并写进 `问题记录-04` **#7**：通道 `Aborted` 后，邮件汇总每 30 秒带着一次完整 Agent 轮次重试，**失败不产生任何代价信号**（不冷却、不熔断、不标记），于是失败态越久烧得越多。

**现状**

- **没有任何额度 / 成本闸门**：全仓搜 `Budget` / `Cost` / `额度` 只命中注释，代码里不存在上限判断；
- 只有「事后可见」的指标：`Kind` 维度的次数 / token 已入库（`MetricFacts`、`SqliteMetricsStore`），但**没有金额**（金额只在供应商后台看）；
- 也没有「异常用量」的报警：唯一上报通道是本轮新提的 R-01，且它还没实现。

**期望形态**

1. **可选开关**的额度上限（默认关闭，开了才管）；
2. 上限可按 **窗口**（小时 / 日 / 月）与 **计量口径**（token / 次数 / 金额）配置；
3. 触达上限后有**明确动作**（硬停 / 只暂停非关键调用 / 只报警）；
4. **报警**复用 R-01 的多通道降级上报：先阈值预警（如 70%），再硬线（100%）；
5. 被拦下的调用要**留痕**（哪一类调用、被谁拦的），否则"为什么不回消息"会变成新的排障黑洞。

**待拍板**

| # | 问题 | 选项 / 代价 |
|---|---|---|
| 1 | 计量口径 | **token**（本地已有，零新依赖，但与 ¥ 不直接对应）/ **金额**（直观，需要本地价目表并跟着供应商调价维护）/ 次数（最粗） |
| 2 | 窗口 | 小时（拦突发，如本次 30 秒循环）/ 日（贴合账单）/ 月（预算感强）；支持几档要看配置复杂度 |
| 3 | 超限动作 | 硬停（安全，但可能"人找不到机器人"）/ 只暂停**非关键**调用（邮件汇总、压缩、定时润色），保留真人对话（体验好，需要给每个调用点标"关键/非关键"）/ 只报警不停 |
| 4 | 关键性分级 | 谁算关键：真人消息回复、命令（`/status`）算；邮件汇总、后台压缩、定时润色、漂移重试算非关键。**这张表要定下来，否则上限拦不住该拦的** |
| 5 | 失败重试是否计入 | 本次事故里一半成本来自"重试"（漂移重试 + 每 30 秒重跑）。建议**重试与非关键调用共用一个小配额**，避免正常对话被重试吃掉 |
| 6 | 默认值 | 开关默认关（尊重"可选"）还是默认开一个小额度（防事故）—— 这条直接决定事故能不能被自动挡住 |

**验收口径（草案）**

- 开关关闭时行为与现在**完全一致**（不得偷偷限流）；
- 打开后，把额度调到 1（或把阈值调到极低），任意一条真人消息仍能正常回复，而邮件汇总 / 压缩被拦下并留痕；
- 到达预警阈值 → **一条**报警（去重，不是每条调用报一次）；到达硬线 → 停止对应类别并再报一次；
- 计数可读回：客户端能看见「本窗口已用 X / 上限 Y」，且与 metrics 对得上；
- 进程重启后计数**不丢**（落库，不是内存计数）。

**影响面**：调用入口唯一化 —— 想法是同形包一层 `DelegatingChatClient`；⚠️ **更正**：仓库里**并不存在** `DriftGuardChatClient`（只在 `docs/03-设计/Agent设计.md` 写过，`grep` 全仓 `.cs` 0 命中），当前唯一包裹层是 `FunctionInvokingChatClient`（`ChatClientFactory.cs:59`）。所以这是**新机制**，不是照抄先例。指标已有 `Kind` + token，够用。**不触碰接缝 A/B/C**，纯 Agent 侧。属于 `FR-10 可观测与运维` 的延伸，拍板后需补写它的验收项。

**2026-11-05 拍板增补（D-01 / D-03 / D-13）**

- **计量口径双轨，余额优先**：定时轮询 DeepSeek `GET /user/balance`（该接口**只返回当前余额快照**，没有历史也没有用量）→ 相邻采样差（扣除充值/赠金增量）推算窗口花费；余额不可用或非 DeepSeek 端点时**自动回落** token × 本地价目表。采样默认 **10 分钟**。

- **默认值**：开关**默认关**；开启时默认**日窗口**，70% 预警 / 100% 停非关键；默认金额由用户后续给一个数（方案文档 §11.2 第 1 项）。
- **余额看板的额外收益**：`is_available=false`（余额见底）本身就是一条硬事实，可直接触发 `QuotaHardStop` 与报警，不依赖 token 估算。

### R-13 错误归因与失败短路（2026-11-05 追加）

**来源（原话）**

「出错重试要搞清楚是哪里出错了，如果是通道本身的问题那就不应该再白白消耗 tokens，出错达到阈值后要通过别的可用通道通知主人，不过可以通过余额检测的方式实现（优选路径），token 用量作为保底。」

**背景**

`问题记录-04` #7 的 11-05 事故里，一半成本来自「重试」：通道发不出去 → `sent == 0` → 判定为「指令遵循漂移」→ **再叫一次模型**（`ChatAgent.cs:399-421`）。整条链上没有一个环节回答「这次失败是通道的错，还是模型的错」。

**现状（缺口）**

- **没有「通道不可用」这个语义异常**：发送失败表现为 `TimeoutException` / `InvalidOperationException` / `WebSocketException` / NRE，甚至是 `WebSocketDuplexBase.SendAsync` 的**静默 return**（`:150-158`）；
- `ChatAgent` 的 `catch (Exception)` 吞掉一切（含取消），**失败连指标行都不写**（`:385-389`；`CallLlmAsync` 只在成功时 `RecordAsync`）；
- `SendMessageTool` 把发送异常转成字符串回填给模型，`sent` 保持 0 → 直接触发漂移重试（`SendMessageTool.cs:95-111`）；
- 没有连续失败计数 / 熔断 / 冷却（全仓 `CircuitBreaker` 0 命中），`SchedulePoller` 失败每分钟无限重试（`:114-119`）。

**期望形态**

1. **错误分类**：每条失败落到一个 `FailureKind`（通道不可用 / 发送失败 / 目标非法 / 限流 / 模型瞬时 / 模型致命 / 内容非法 / 未知）；
2. **失败短路**：通道不可用时**不再触发漂移重试**；按连续失败阈值**分级**短路（一级只停非关键路径，二级停该通道全部 Agent 轮次）；
3. **达阈值上报**：走 R-01 的多通道降级链通知主人（QQ → 抖音 → 落库 + 客户端）；
4. **留痕**：短路、拦截、失败都进指标与审计，能回答「为什么不回消息」。

**待拍板（已定，见 §6 D-02）**

| # | 问题 | 结论 |
|---|---|---|
| 1 | 短路范围 | **阈值渐进**：一级非关键（邮件汇总 / 压缩 / 漂移重试 / 定时润色）；二级该通道全部轮次 |
| 2 | 「达阈值」的判据 | 连续失败次数 + 时间窗（默认一级 3 次 / 60 秒，二级 10 次 / 5 分钟），可配 |
| 3 | 与额度闸门的关系 | 两者共用「非关键」分类表；任一触发都停非关键 |

**验收口径（草案）**

- 通道进入 `Aborted` 后，`llm.call` / `llm.retry` 计数**不再增长**（这是 11-05 事故的直接反例）；
- 每次失败都能读出 `FailureKind`，且「通道问题」与「模型问题」不混淆；
- 二级阈值触发后：该通道的 Agent 轮次不再调模型，入站消息入队并在恢复后合并处理；
- 短路与拦截都有指标 + 审计，客户端或 `/status` 可见。

**影响面**：`Transport`（状态守卫）、`Channel`（语义异常）、`Agent`（重试判据 / 工具回填）、`Server`（冷却与告警）。**不触碰接缝 A/B/C**。
