## 1. 产品定位

一款**角色扮演型 AI 助手**：以 QQ 群聊与私聊为入口，由 AI 以**固定人设**参与对话；AI 通过**调用工具**主动发送消息，而非被动返回文本；全部对话上下文与记忆由系统自行管理，使 AI 能**记住跨会话的历史**。

一句话边界：**AI 负责"想说什么"，平台负责"怎么送出去"。**

---

## 2. 角色与场景

| 角色 | 说明 | 典型诉求 |
|---|---|---|
| **群成员** | 群内任意成员，可与 AI 对话 | 被叫到时得到符合人设的回应 |
| **私聊用户** | 与 AI 一对一 | 连续、深入的对话；记得之前说过的事 |
| **白名单成员** | 被授予额外工具权限的个体 | 让 AI 在自己的工作区读写文件 |
| **管理员** | 系统所有者 | 配置、查看日志、全量权限 |

## 3. 功能需求

> 优先级：`M1` = 首版必须；`M2` = 次版
> 每条需求**必须**有可测的验收标准，不接受"体验更好"这种描述。

### FR-1 通道抽象（多平台可移植） `M1`

**需求**：消息收发必须经**平台无关**的抽象层；QQ 只是它的第一个实现。后续接入其他社交平台时，**上层（会话、AI、工具、权限）不得改动**。

**消息类型范围：仅文本 + 图片。**
语音由**通道层负责转成文本**后再进入上层（上层不感知语音）；具体 STT 路径见 §8.2 D-11。

| # | 验收标准 |
|---|---|
| 1.1 | 上层代码中 `grep` 不到任何平台专有名词（`NapCat` / `OneBot` / `QQ`） |
| 1.2 | 新增一个平台实现，只需新增一个项目 + 一行注册，不改动 Agent / 会话 / 工具层 |
| 1.3 | 消息模型平台无关，覆盖：**文本、图片**、@提及、回复引用 |
| 1.4 | 通道**声明自身能力**（支持哪些消息类型），工具参数描述按能力动态生成 |
| 1.5 | 语音消息在通道层被转为文本；**上层代码不出现语音相关分支** |

> **1.4 的理由**：否则模型会给一个不支持图片的平台发图片，白费一次调用。

### FR-2 消息发送（AI 主动调工具） `M1`

**需求**：AI **不通过"返回文本"来回复**，而是调用 `send_message` 类工具主动发送；工具在调用时由平台注入**当前会话与发送者身份**。

| # | 验收标准 |
|---|---|
| 2.1 | AI 一轮运行结束且**未调用**任何发送工具时，若存在最终文本，则**兜底自动发送**（可配关闭） |
| 2.2 | 同一条消息**不得重复发送**（重试机制不得重放已成功的发送） |
| 2.3 | 发送失败时向 AI 回填失败原因（而非抛异常中断整轮） |
| 2.4 | 支持一条回复**分段发送**（长文本切分），切分不破坏 Markdown / 代码块 |

> **2.1 是硬保险**：模型不调工具就彻底沉默，在群里等于"叫了不理人"。

### FR-3 会话与上下文 `M1`

**需求**：所有上下文由系统自行管理，**不使用服务端会话保持**（不使用 `previous_response_id`）。上下文分三层：

| 层 | 内容 | 保留策略 |
|---|---|---|
| **热** | 最近 N 轮原文 | 固定保留，**永不压缩**（N 可配，默认建议 20 轮） |
| **温** | 更早对话的**结构化摘要** | 滚动更新，**后台异步**生成 |
| **冷** | 全量原文入库（SQLite），上下文中只留索引 | 按需检索 |

| # | 验收标准 |
|---|---|
| 3.1 | 两个不同会话（不同群 / 不同私聊）的上下文**绝不串** |
| 3.2 | 压缩后上下文仍在 token 预算内；**系统人设消息永不被压缩丢弃** |
| 3.3 | 压缩在**后台**完成，**不阻塞**当轮回复 |
| 3.4 | 全量消息（含命令消息与命令响应）持久化，重启后可恢复 |
| 3.5 | 同一会话的多条消息**串行处理**，不产生上下文竞争 |
| 3.6 | 跨会话检索可配置开启/关闭；返回结果**带会话索引**，标明来源会话 |
| 3.7 | **每个聊天拥有独立的 agent 实例与独立上下文**；实例可被卸载并从库重建，**重建后行为等价** |

### FR-4 历史检索 `M1`

**需求**：两件事 —— ① AI 可主动调用的检索工具；② **调用 LLM 前的自动预取**。

| # | 验收标准 |
|---|---|
| 4.1 | 检索工具支持按关键词 / 时间范围 / 会话范围查询 |
| 4.2 | 命中结果自动**扩展上下文窗口**（命中条目前后各 K 条），不只返回单条 |
| 4.3 | **自动预取**：用户消息命中指代词（"之前/上次/还记得/那个"等）或配置关键词时，在调用 LLM 前自动检索并注入，**不依赖模型主动调用** |
| 4.4 | 预取命中为空时**不注入**任何内容（不产生噪声 token） |
| 4.5 | 预取与工具调用的总耗时纳入可观测指标 |

> **4.3 是本需求的核心假设**：把"要不要查历史"的判断从模型手里拿回来，用确定性规则替代模型的自我评估。

### FR-5 人设（**两层：全局 + 聊天**） `M1`

**需求**：人设必须**稳定贯穿长对话**。人设分两级，**聊天级覆盖全局级**：

| 层 | 存放位置 | 生效规则 |
|---|---|---|
| **全局人设** | 运行配置 | 默认生效 |
| **聊天人设** | 该聊天的会话配置 | **有值时完全取代全局人设**（不合并） |

**为什么是「完全覆盖」而不是「字段合并」**：合并会产生"哪一句在生效"的模糊地带，一旦人设串味极难排查。完全覆盖的语义可预测。若日后确需部分覆盖，再引入"继承 + 显式字段覆盖"（见 §8.2 D-10）。

人设本身分**核心卡**（200–300 字，恒定携带）与**细节**（按需注入）两段。

| # | 验收标准 |
|---|---|
| 5.1 | 人设分核心卡与细节两段；核心卡随每轮携带 |
| 5.2 | 每隔 N 轮（默认 10，可配）**重新注入**人设，位置紧邻**最新用户消息之前** |
| 5.3 | 上下文中恒定只有 **2 条**人设消息：**首条锚点（永久）+ 最近一次重注入** |
| 5.4 | 会话从数据库恢复时**必做一次**重注入 |
| 5.5 | 人设变更（热更新）后，下一轮即生效，且**不残留旧人设** |
| 5.6 | 可观测：能统计"人设漂移检测"的触发次数与会话分布 |
| 5.7 | 全局人设在**未配置聊天人设**的聊天中生效 |
| 5.8 | 聊天人设有值时，**全局人设不参与**该聊天的上下文 |
| 5.9 | 清除聊天人设后，**下一轮回落到**全局人设，旧人设不残留 |

### FR-6 工具与权限（**可配置**） `M2`

| # | 验收标准 |
|---|---|
| 6.1 | 权限主体是**消息发送者**，不是会话（群内谁说话，权限就是谁的） |
| 6.2 | 三层角色：管理员 / 白名单 / 普通；**默认拒绝**（deny-by-default） |
| 6.3 | 工具声明**能力等级**（读文件 / 写文件 / 执行命令 / 访问网络），门禁校验**能力 + 参数 + 路径**，不只校验工具名 |
| 6.4 | 权限不足时向 AI 回填说明（而非抛异常），使 AI 能换方式回答 |
| 6.5 | **每个工具的最低可用角色可在配置中调整**（如把某个只读工具开放给普通成员） |
| 6.6 | ⚠️ **配置存在硬底线**：高危能力（执行命令 / 写文件 / 访问网络）**不允许**被配置为对普通成员开放；越界配置在**启动时**报错拒绝 |
| 6.7 | 提供"预置默认允许集"，降低逐项配置负担 |

> **6.6 的意义**：「可配置」不等于「可以配成危险」。软配置之上必须有一条不可配置的硬底线，否则一次手滑就是沙箱失守。

### FR-7 工作区与文件沙箱 `M2`

| # | 验收标准 |
|---|---|
| 7.1 | 存在一个**总工作区**目录；其下按平台 → 群聊/私聊 → 会话 ID 分目录 |
| 7.2 | **路径穿越攻击必须被拦截**：`..`、绝对路径、符号链接逃逸一律拒绝 |
| 7.3 | 管理员可写全部会话目录；白名单成员仅可写**自己当前会话**的目录 |
| 7.4 | **读权限不得默认全开** —— 跨会话读取须管理员权限（见 §8.1 R1） |

### FR-8 配置（引导层 / 运行层） `M1`（分层）/ `M2`（UI）

| # | 验收标准 |
|---|---|
| 8.1 | **引导配置**（监听地址、鉴权 token、**LLM API key**）只存在于服务端配置文件 / 环境变量，启动必需，缺失即拒绝启动 |
| 8.2 | **运行配置**（其余全部，含模型名与端点）存于服务端，**只由客户端 UI 写入**，与引导配置**不重叠** |
| 8.3 | 客户端首次启动只需两项：**服务器地址 + token** |
| 8.4 | 运行配置变更后**无需重启**生效（至少 LLM 参数 / 人设 / 上下文参数） |
| 8.5 | 客户端 UI 保存配置时**校验**并返回明确错误（不是静默失败） |
| 8.6 | ⚠️ **API key 永不进入 UI、网络报文与数据库** —— 只能由引导层读取 |

> **8.1 / 8.2 的分层是硬要求**：同一项配置存在两个可写来源，必然产生"改了不生效"的故障。**本项目已因此吃过两次亏。**
> **8.6 的理由**：key 一旦进 UI，就要在网络上传输、在库里落盘，攻击面成倍放大。

### FR-9 命令系统 `M2`

| # | 验收标准 |
|---|---|
| 9.1 | 以 `/` 开头的消息**先**匹配命令；匹配则**不**交给大模型 |
| 9.2 | 未匹配到任何命令时，**按普通消息**交给大模型处理，用户无感知 |
| 9.3 | 命令消息与命令响应**都持久化**，且后续对话中模型**能看到** |
| 9.4 | 命令结果不得伪装成 AI 自己的发言（避免模型后续误认为"是我说的"） |
| 9.5 | 命令可扩展：新增命令 = 新增一个类 + 一行注册 |
| 9.6 | 命令按角色鉴权（见下表） |

**首批命令（参考稿，待确认）**：

| 命令 | 作用 | 最低角色 | 类别 |
|---|---|---|---|
| `/help` | 命令列表 | 所有人 | 只读 |
| `/status` | 模型 / token 用量 / 压缩次数 | 所有人 | 只读 |
| `/persona` | 查看当前生效人设 | 所有人 | 只读 |
| `/remember <文本>` | 写入长期记忆 | 所有人 | **写** |
| `/search <关键词>` | 检索历史 | 所有人 | 只读 |
| `/persona set <id>` | 设置**本聊天**人设 | 管理员 | **写** |
| `/mode <模式>` | 切换回复触发模式 | 管理员 | **写** |
| `/compact` | 立即压缩上下文 | 管理员 | 写 |
| `/reset` | 清空本会话上下文（**保留日志**） | 管理员 | 写 |
| `/forget <id>` | 删除一条长期记忆 | 管理员 | **写** |
| `/export` | 导出本会话日志 | 管理员 | 读 |
| `/purge` | 删除本会话日志 | 管理员 | **删除** |

> **读写是基本盘**：`/remember`、`/forget`、`/search` 三件套构成记忆的最小闭环。

### FR-10 可观测与运维 `M1`（最小）/ `M2`（完整）

| # | 验收标准 |
|---|---|
| 10.1 | 每轮对话可追溯：触发消息 → 上下文构成 → LLM 调用 → 工具调用 → 发送结果 |
| 10.2 | 日志**写盘前脱敏**（token / API key 可配；QQ 号按需） |
| 10.3 | 能观测到：轮次延迟、token 用量、压缩次数、检索命中率 |

### FR-11 回复触发模式（**四种，可配置**） `M1`

**需求**：每条聊天可独立配置"什么时候让 AI 说话"，全局有默认值。

| 模式 | 触发条件 | 每条消息的模型调用 | 适用场景 |
|---|---|---|---|
| `mention` | 仅被 **@** 或命中唤醒词 | 未命中时 **0** | 大群，避免刷屏 |
| `every` | **每条消息**都触发 | 1 次对话 | 私聊、小群 |
| `schedule` | 按**周期**自动触发 | 按周期计 | 定时播报 / 主动搭话 |
| `jev` | 先由 **JEV 判断**"该不该回"，判定为是才触发 | **1 次判断** + 命中时 1 次对话 | 想让它"自然插话" |

| # | 验收标准 |
|---|---|
| 11.1 | 四种模式均可配置并生效 |
| 11.2 | 配置粒度：**全局默认 + 每聊天覆盖** |
| 11.3 | 模式切换**下一轮即生效**，无需重启 |
| 11.4 | ⚠️ **`jev` 模式必须可降级**：JEV 服务不可用 / 超时时，回落到配置的备用模式（默认 `mention`），**不丢消息、不阻塞** |
| 11.5 | `jev` 的判断结果（回 / 不回 / 判断耗时）记入会话日志与指标 |

> **成本提醒**：`every` 与 `jev` 都会让成本随群活跃度线性上升。`jev` 比 `every` 多一次判断调用，但能在"不该说话"时省掉整轮对话 —— 对活跃群通常更省。

### FR-12 会话思考日志 `M1`（记录）/ `M2`（导出与删除）

**需求**：不做流式展示；**把每轮的思考过程写进会话日志**，并支持导出与删除。

| # | 验收标准 |
|---|---|
| 12.1 | 每轮记录：触发原因、上下文组成摘要、模型思考内容、工具调用与结果、最终发送的消息、耗时与 token |
| 12.2 | 支持导出（JSON + Markdown 两种） |
| 12.3 | 支持删除：按会话 / 按时间范围 / 全部；**删除后不可恢复，且不残留在检索索引中** |
| 12.4 | 日志写入失败**不阻塞**回复（只记警告） |
| 12.5 | 思考内容可能含他人隐私 → 导出与删除操作**均需管理员权限** |

> **12.3 的坑**：SQLite 删除后旧页可能仍在文件中。需要 `VACUUM` 或安全删除流程，否则"删了还能捞出来"。

### FR-13 发送者识别与好友联想 `M1`

**需求**：群聊里 AI 必须知道「这句话是谁说的」，并能把人**认准**、必要时**联想起**与他的其它对话。

| # | 验收标准 |
|---|---|
| 13.1 | 每条消息携带发送者标识：**账号 ID**、**群昵称（card）**、**QQ 昵称（nickname）**、**是否好友** |
| 13.2 | 呈现给模型的发送者信息**同时包含群昵称与本名** —— 群昵称经常改，只给一个必然认错人 |
| 13.3 | 提供 `get_user_info` 工具，按账号查资料（群聊与私聊都可用） |
| 13.4 | 群聊发送者是**好友**时，检索能力可**跨会话**关联到该人的私聊历史（需开启跨会话检索） |
| 13.5 | ⚠️ 好友联想**不自动注入私聊内容**，只在检索命中时注入片段 |

> **13.5 是关键约束**：把好友的私聊内容自动塞进群聊上下文 = 当众念私信 + 上下文爆炸。必须是**按需检索**，不是默认携带。

### FR-14 定时任务 `M2`

**需求**：AI 可创建 / 删除定时任务；系统按**分钟精度**轮询执行。

| # | 验收标准 |
|---|---|
| 14.1 | 提供创建与删除任务的工具；任务**持久化在数据库**，重启不丢 |
| 14.2 | 轮询周期 **1 分钟**，任务触发精度到分钟（做不到"30 秒后提醒"） |
| 14.3 | 支持**一次性**与**周期性**任务 |
| 14.4 | 任务完成后可向指定会话发送结果；群聊可 **@ 指定成员** |
| 14.5 | 服务停机期间错过的任务，重启后**补执行一次**；周期任务不雪崩（只补最近一次） |
| 14.6 | 任务创建 / 删除**受权限控制**（默认管理员） |

**队列实现结论：数据库即队列。** `next_run_at` 建索引，每分钟一次：

```sql
SELECT * FROM ScheduleTask
WHERE status = 'pending' AND next_run_at <= :now
ORDER BY next_run_at
```

- **不需要额外的内存队列** —— 单实例部署、重启不丢、可直接在客户端 UI 列出与删除
- 内存队列会引入「DB 与内存两份真相」，本项目已在这上面吃过两次亏
- SQLite 几千行带索引查询 < 1ms，1 分钟轮询毫无压力

> **14.6 的风险**：普通成员若能创建定时任务，等于给了他「定时刷屏」的能力 —— 群里到点就被 @ 一次。默认仅管理员，白名单需显式开启。

## 4. 非功能需求

| 维度 | 要求 |
|---|---|
| **延迟** | 单轮回复（不含长工具调用）目标 **< 5 秒**；压缩与预取不得显著增加首字延迟 |
| **成本** | 默认档位**不产生额外 LLM 调用**；高成本特性默认关闭 |
| **安全** | 默认拒绝；路径穿越必须拦截；**硬底线不可配置绕过** |
| **可移植** | 服务端跨平台（Windows + Linux）；客户端 WPF（Windows-only） |
| **可恢复** | 进程重启后会话与上下文可恢复，人设不丢 |
| **数据** | 全部消息本地 SQLite；不依赖任何外部会话存储 |
| **隐私** | 思考日志可彻底删除；导出需授权 |

## 5. 范围边界（明确不做）

| 不做 | 原因 |
|---|---|
| Web 客户端 | 本期不考虑（用户明确） |
| **对话流式展示到 QQ** | QQ 消息不可编辑；思考内容只入日志（FR-12） |
| 多用户账号体系 / 登录 | 单管理员的本地部署；客户端用 token 鉴权 |
| 云同步 / 多实例共享会话 | 单实例，SQLite 本地 |
| 语音消息的语音识别（在上层） | 由**通道层**转文本，上层不感知（FR-1.5） |
| 视频 / 直播等重媒体 | 超出「文字 + 图片角色扮演」范围 |

## 6. M1 范围与阶段切分

> 用户选定 M1 = **QQ 私聊 + 群聊 + 人设 + 三层上下文**。
> **原则**：每阶段**独立可交付、独立可验收、随时可停**。

| 阶段 | 内容 | 验收标志 |
|---|---|---|
| **M1-A 骨架与通道** | 项目骨架、消息模型（文本+图片）、QQ 通道、收消息落库 | **能收到真实 QQ 消息并入库**，上层无平台名词 |
| **M1-B LLM 闭环** | Responses API、单轮对话、`send_message` 工具、兜底发送、**回复模式 `mention` / `every`**、**发送者识别（FR-13）** | **私聊一问一答**；**群里 @ 它才回**，且能叫对是谁在说话 |
| **M1-C 会话与上下文** | 会话隔离（群/私聊）、三层上下文、检索工具、自动预取、**好友跨会话联想** | **压缩不丢人设**；"上次说的"答得上 |
| **M1-D 人设** | 全局 + 聊天双人设、周期重注入、漂移检测（L0/L1） | **连聊 30 轮人设不崩**；切人设后不串味 |

> **`jev` / `schedule` 已定放 M2**（D18）—— 它们不影响主链路跑通，但各自依赖外部服务或调度器。
